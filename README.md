# slicc-vault

The separate-origin vault at `vault.sliccy.ai`. It holds the sealed secrets, OAuth tokens, and model and MCP credentials of SLICC seven, so that no value ever reaches the model provider. The design is `secrets-tokens-design.md` (revision 4) in slicc-agent-plan. This README is the spec of what is built.

- **Built:** the key store, records, origin namespacing, auto-unlock with an optional passkey or passphrase lock, the embedding API with its `page` and `agent` roles, the page's `put`, `enter`, `seal`, `remove`, `restore`, `forgetLease`, `cancel` and `lock`, the scrub state, the lock button and its popup, the value frame for asks, the attested policy (rules, `[exec]`, `[exits]`, `[limits]`, `[reveal]`), the injector and `forward` with the response scrub (S1), the agent's `redact`, `redactStream`, `endpoints`, `model` and `mcp` (S3, S4), `records`, `grant` and `refresh`, the model and MCP refusal, exec tickets (`materialize` and `materializeConsume`), `sessionMaterialize` for kernel-verified TLS sessions, `import` (backups, KeePass, six's `secrets.env`) and `export`, sign-in tokens with their grants and refresh through `egress`, and the vault side of the `/dev/sealed` ops `seal`, `placeholder`, `list`, `test`, `request`, `ask`, `status`, `cancel`, `materialize`, `capabilities`, `oauthGrant`, `oauthStatus`, `oauthRefresh` and `oauthRemove`.
- **The vault has no network stack.** It never fetches anything but its own `config.json` and `embedders.json`: bios sends every request the vault prepares.

## Documents and hosting

The build (`npm run build`) writes a flat static tree to `dist/site/`:

| file | what it is |
|---|---|
| `index.html`, `frame.js` | the core frame. bios embeds it as a hidden iframe and talks to it over a `MessagePort` |
| `button.html`, `button.js` | the lock button. A popup can only open from a click inside a vault document, so bios and spectrum embed this wherever the lock is offered |
| `value.html`, `value.js` | the value frame. spectrum shows it inside the dialog of an `ask`: the user types a value or allows a reveal there, never in seven's page |
| `popup.html`, `popup.js` | the vault window, a top-level `vault.sliccy.ai` document, used only for the passkey or passphrase lock |
| `vault.css`, `fonts/` | Spectrum 2 from the CSS-only `@spectrum-css` packages, and Adobe Clean |
| `config.json` | `{ version, embedders }`. `embedders` is `vault.sliccy.ai`'s fallback list, `["https://seven.sliccy.ai"]` |

The bundles hold this repo's code, `@ai-ecoverse/slicc-scrub`, and `@ai-ecoverse/jerk-oauth` (exact-pinned, for token refresh): its wasm is inlined into a separate chunk under `chunks/` (about 970 KB) that loads only on the first refresh or MCP `grant`, never fetched. The only third-party code is for KeePass imports: `kdbxweb` (with `@xmldom/xmldom` and `fflate`) and `hash-wasm`'s argon2, exact-pinned and bundled into a separate chunk under `chunks/` that the core frame loads only when a KeePass import starts; its wasm is inlined, never fetched. The sliccy-ai Worker serves the tree from the network on every load, never from OPFS, with:
- `Content-Security-Policy`: `default-src 'none'`; `script-src 'self' 'wasm-unsafe-eval'`; `style-src 'self'`; `img-src 'self' data:`; `font-src 'self'`; `connect-src 'self' https: http://localhost:* http://127.0.0.1:*`; `worker-src 'self'`; `manifest-src 'self'`; `base-uri 'none'`; `form-action 'none'`; and `frame-ancestors` set to the embedder sources, space-separated. A source is `http://` or `https://` plus a host, optionally `:port` or `:*`. An empty list is `'none'`. On `vault.sliccy.ai` the list is `https://seven.sliccy.ai` and `https://www.sliccy.ai`;
- `Cross-Origin-Embedder-Policy: require-corp`, `Cross-Origin-Resource-Policy: same-site`, `Cross-Origin-Opener-Policy: same-origin`;
- `Origin-Agent-Cluster: ?1`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-cache` with an ETag on each stored object, and `Cache-Control: no-store` on the HTML documents (`/`, `index.html`, `button.html`, `value.html`, `popup.html`);
- content types `application/wasm`, `font/woff2`, `text/javascript; charset=utf-8`, `text/css; charset=utf-8`, `application/json` and `text/html; charset=utf-8` for `.wasm`, `.woff2`, `.js`, `.css`, `.json` and `.html`, `application/json` for a linked source map (`.map`), and `text/plain; charset=utf-8` for linked legal text (`.txt`, including `.LEGAL.txt`).

The npm package ships that tree as `dist/site` and this header table as `dist/headers.json`. `exports` stays types-only (`dist/types/contract.d.ts`): a consumer does not import the site. It serves the files in `dist/site` from the installed package and answers `GET /embedders.json` itself, because that file is not in the tree. `dist/headers.json` is written at build by `scripts/headers.mjs`, and `test/integration/serve.mjs` reads that same module, so the package and the tests stay one table. Each path class (`documents`, `scripts`, `css`, `maps`, `text`, `fonts`, `wasm`, `config.json`, `embedders.json`) records the CSP, including the `frame-ancestors` shape above, COOP, COEP, CORP, `cache-control`, `x-content-type-options`, `referrer-policy`, `origin-agent-cluster` and the content type. Its `embedders` object is the `/embedders.json` body, `{ "embedders": [...] }`. Its `config` object is the `config.json` shape, `{ version, embedders }`; the built `config.json` uses `["https://seven.sliccy.ai"]` as the fallback list. On `vault.sliccy.ai`, `/embedders.json` is the same two origins as `frame-ancestors`.

The Worker also sends `Strict-Transport-Security: max-age=31536000`, the stored object's `ETag` (not on `/embedders.json`) and `x-sliccy-ai-version`. The local server does not send those. `dist/headers.json` records them under `productionOnly`. Cloudflare adds its own edge headers. The bullets above are the vault contract.

To stay out of the back/forward cache, `index.html`, `button.html` and `value.html` add an `unload` listener, which keeps an embedder's page out of it too, and all four documents reload on a `pageshow` with `persisted`; `bfcache.test.mjs` proves `index.html` is never restored.

At start, a vault document that is the top-level document (`popup.html`, or `index.html`, `button.html` or `value.html` opened as a tab) calls `navigator.mediaDevices.setCaptureHandleConfig({ handle: 'slicc-vault', exposeOrigin: true, permittedOrigins })`, with `permittedOrigins` the embedders the document loaded that are valid exact origins, serialized (a `:*` source or an invalid one is left out; none means an empty list, never `'*'`), so seven sees the handle and refuses to capture a vault tab. A framed document, or a browser without the API, sets none.

`GET /embedders.json` is answered by the Worker, not by this tree. It returns `{ "embedders": [...] }`, the same sources as `frame-ancestors`. The vault reads it at start and accepts only those origins. When it's missing or malformed, only `vault.sliccy.ai` falls back to `config.json`; on every other host (`vault-preview.sliccy.ai`, branch previews, local) that means no embedders, so it fails closed. An embedder source is `http(s)://host`, optionally with `:port` or `:*`, matched exactly.

`main` is served at `vault.sliccy.ai`, and every other branch at `vault-<label>.sliccy.ai`. CI is one caller workflow, `ci.yml`, that runs slicc-shared-web's `pipeline.yml` at the same v2 tag as the `@ai-ecoverse/slicc-shared-web` devDependency, with `secrets: inherit`, on pull requests, on the merge queue (`merge_group`) and on `main`: lint everywhere; on pull requests and in the merge queue the integration tests (`test/integration/*.test.mjs`, split by timings across the pipeline's shards, Chrome for Testing from `slicc-cdp install-browser`, headed on Xvfb); on pull requests a Claude and a Codex review; on `main` semantic-release, with no tests. `ci / integration` and `ci / review` are the checks to require. The pipeline picks its own runners (its self-hosted pool, a hosted runner for a fork's pull request and for the release), and a pull request from a fork gets no review. Releases run only on `main`: the pipeline's release job runs only on a push to it, in the `production` environment, and publishes `vault.sliccy.ai` there. On a pull request the pipeline's `deploy` job publishes the branch preview in the `staging` environment and hands its URL to the tests and reviewers as `STAGING_URL`; it publishes nothing to npm and makes no tag or release, and the merge queue deploys nothing. `ci.yml` is the only workflow, so nothing deploys outside the pipeline. No workflow names a self-hosted runner label. `workflows.test.mjs` keeps all of this so. seven embeds only `vault.sliccy.ai`.

## Storage and keys

Everything lives in the vault origin's IndexedDB, database `slicc-vault`, version 1:

| store | key | holds |
|---|---|---|
| `meta` | `"keys"` | the key state below |
| `records` | `[ns, kind, name]`, unique index on `placeholder` | records |
| `requests` | `id` | requests that wait for a human |
| `audit` | `seq` (auto-increment) | the audit log, per namespace |
| `intents` | `nonce` | hand-offs from a button to the popup, valid for 10 minutes |

**The data key** is one AES-GCM 256 key. Each record's value is encrypted under it with a fresh 12-byte IV and the additional data `slicc-vault/1 NUL ns NUL kind NUL name`, so a ciphertext can't be moved to another record.

**The key state** is one of:
- `auto` (the default): the data key is stored as a **non-extractable** `CryptoKey`. Every vault document loads it at start, so there's never a prompt.
- `passkey`: the data key is stored only wrapped (AES-GCM) under a key-encryption key from **WebAuthn PRF**. The passkey's RP id is the vault's host, the PRF input is a random 32-byte salt, and the KEK is HKDF-SHA-256 over the PRF output with that salt and the info `slicc-vault/kek/1`.
- `passphrase`: the same, with the KEK from PBKDF2-SHA-256, 600,000 iterations, over a random 16-byte salt.

**Locking:**
- While protected, a document starts locked and asks the other open vault documents (over the origin's `BroadcastChannel` `slicc-vault`) for the unwrapped key. Unlocking in the popup unwraps the key as non-extractable and hands it to every open vault document the same way.
- `Lock now` drops the key from every document. Closing every vault document has the same effect.
- **Protecting** makes a new data key, re-encrypts every record under it, and stores it wrapped, in one transaction. If a record changed meanwhile, protecting fails with `EAGAIN` and changes nothing. **Removing protection** stores the current key as non-extractable again.
- Every data key has an id, stored with it. A seal checks that id in the same transaction that writes the record, so a value encrypted under a key that was replaced meanwhile is refused with `EAGAIN` rather than stored unreadable.
- While locked, `seal` answers `EACCES` with a message starting `vault is locked`. Ops that need no value (`placeholder`, `list`, `status`, ...) still work.

## Records

```
{ ns, kind: "secret" | "grant" | "model" | "mcp", name, placeholder, sealed: { iv, data },
  source, createdAt, updatedAt, usedAt?, expiresAt?, refresh?, oauth?, provider?, server?, settings?, url?, sealedBy?, removedAt?, removedWith?, lease? }
```

- **`ns`** is the embedder's origin, below.
- **`name`** matches `^[A-Za-z_][A-Za-z0-9_]*$`, at most 128 characters.
- **A value** is at least 8 bytes of UTF-8, without CR, LF or NUL, and contains no placeholder. Anything shorter is refused with `EINVAL` "values shorter than 8 bytes can't be protected from the model", because the scrubber couldn't tell it apart from ordinary output.
- **`placeholder`** is `fnox_proxy_` plus 24 lower-case hex characters from `crypto.getRandomValues`, unique across the whole vault and stable for the record's life. All placeholders have the same length, so none contains another.
- **`provider`** (a `model` record's pi-ai provider id, required, `^[a-z0-9][a-z0-9._-]{0,63}$`), **`server`** (an `mcp` record's MCP server name, optional) and **`settings`** (non-secret `NAME = text` pairs for a `model` or `mcp` record, at most 16, each at most 256 characters, e.g. `AWS_REGION`) bind a record to what may use it. In `list`, a grant shows the `server` or `provider` of the live tokens of the same `source` that name it as their `refresh`, when they all agree (and none when they don't, whatever the grant stored), for display and lookup only; nothing is copied onto the grant. A reseal without them keeps the stored ones, and one with them rebinds the record; a new `model` record without a provider is refused with `EINVAL` "a model record needs its provider".
- **`source`** is `settings` (entered in spectrum), `process`, `jerk:<provider>@<device>`, `oauth:<provider>` or `import:<kind>`.
- **`lease`** (`{ id, node }`, a J1 lease's only) is in Tokens and refresh.
- **`state`** is computed, never stored: `removed` when `removedAt` is set, `active` when the accepted policy has a rule for the record (below), otherwise `inert`.
- **Removing** sets `removedAt`. A removed record keeps its placeholder, can be restored with `restore`, and is deleted for good 30 days later. Sealing a removed name brings it back with a new value and the same placeholder. Removing a token removes the grant its `refresh` names (when the grant has the token's own `source`, and no other live token of that source still names it) in the same transaction, and restoring it restores that grant too, only when that grant was removed by this token's removal (the vault records which token took it as `removedWith`, `<kind>\u0000<name>` of that token, cleared on restore) and is still within the 30 days; the one `remove` or `restore` audit entry names it as `grant`. Removing an already removed record, or restoring a live one, succeeds and changes nothing (its 30 days don't restart, and nothing is audited).
- **Times** are epoch milliseconds everywhere.

## Backup reminder

`status.exportedAt` is the time of the namespace's last successful `export`, or `null` if it never exported. `status.backupReminder` is `due` once the namespace holds a `secret` record and has never exported, `dismissed` after `dismissBackupReminder`, and `null` otherwise (no secrets yet, or exported).

## Policy

The rules come only from two root-owned kernel files. bios reads them with the kernel's page-only `kernel.attest(path)` (KS-7), at boot and whenever either file changes, and passes the results through unchanged:

```js
port.postMessage({ v: 1, id, op: 'policy', files: [await kernel.attest('/etc/fnox/config.toml'), await kernel.attest('/etc/slicc/secrets-policy.toml')] });
```

**An attestation** is exactly `{ path, bytes, uid, gid, mode, ino, mtimeMs, sha256, users, onRootFs, parents }`, nothing more or less:

| field | format |
|---|---|
| `path` | the canonical absolute path the kernel read (it refuses symlinks and mount points) |
| `bytes` | the file's bytes, a `Uint8Array`, read in the same step as the stats |
| `uid`, `gid`, `mode` | integers; `mode` includes the type bits (`0o100644`) |
| `ino`, `mtimeMs` | numbers |
| `sha256` | 64 lower-case hex characters |
| `users` | the kernel's users mode: `off`, `report` or `enforce` |
| `onRootFs` | true only on the root file system, under no mount |
| `parents` | every directory from `/` down to the file's, each exactly `{ path, uid, gid, mode }` |

The vault trusts a file only when:
- `path` is `/etc/fnox/config.toml` or `/etc/slicc/secrets-policy.toml`, and the object has exactly the fields above in those formats;
- the SHA-256 the vault computes over `bytes` equals `sha256` (the field alone is never trusted);
- `uid` is 0, and `mode` is a regular file with `mode & 0o022` of 0;
- `parents` lists exactly the directories above `path`, in order from `/`, each with uid 0, a directory type and `mode & 0o022` of 0;
- `onRootFs` is true, and `users` is `enforce`;
- `bytes` is UTF-8 and parses.

Otherwise the vault keeps the policy it last accepted for that file, so the rules it would have changed stay as they were (new ones stay inert), and warns, e.g. `rules not trusted: /etc/fnox/config.toml: kernel users must be enforce`. The reply is `{ accepted, files: [{ path, sha256, accepted, warnings, absent?, paused? }], rules: [{ secret, domain, header, methods, paths, protocol?, position?, port? }], warnings }`, with `rules` the rules now in effect. `status.policy` repeats `files` from the last `policy` call, so Settings can show why rules aren't trusted.

**A missing file** is attested by the kernel as exactly `{ path, absent: true, users, onRootFs, parents }`, with no other field (so no `bytes`, `sha256`, `uid`, `mode`, `gid`, `ino` or `mtimeMs`). The vault trusts it only when `path` is one of the two files, `absent` is exactly `true`, `onRootFs` is true, `users` is `enforce`, and `parents` lists exactly the directories above `path`, by the same rules as for a file. A list that stops above a missing directory isn't trusted. Anything else with `absent` is an untrusted attestation, as above: the last accepted policy, or a pause, stays as it was.

A trusted one clears the accepted policy of that file and pauses it: while either file is paused, `forward` of a secret, `materialize`, `materializeConsume`, `sessionMaterialize`, `sessionAnchors` and the `test` verdict all refuse with `policy file missing: paused` (`EACCES`, or a `403` from `forward`) and `cause: 'policy-paused'`, so deleting `secrets-policy.toml` never falls back to permissive defaults. `forward` of an `mcp` record uses no rule and goes on. The pause is kept with the accepted policy, and ends when a trusted attestation of that file with `bytes` arrives. Until then `files` and `status.policy` show the file with `absent: true` and `paused: true`, in every `policy` reply, whether or not the call named it.

**The KS-7 conformance fixtures** are `test/integration/fixtures/attest/*.json`: `{ description, trusted, reason?, attestation }`, with `bytes` as base64, written by `make.mjs` next to them. `good-*` must be trusted, and every `bad-*` must be refused with a warning containing `reason`. The vault's own tests run them through the `policy` op, and the kernel's tests can check that `kernel.attest` produces the good shape.

**`/etc/fnox/config.toml`**, the injection policy, read the way fnox reads it:
- `[secrets]`: entries whose `provider` (or the file's `default_provider`) is `seven`, and whose `value` is a placeholder.
- `[[proxy.rules]]`: `secret` (a seven entry of `[secrets]`), `domain` (one exact host, lower-cased), `header` (lower-cased, default `authorization`), `methods` (upper-cased; empty means any) and `paths` (each starting with `/`; empty means any). A rule that breaks any of this is dropped with a warning; the rest of the file still counts. Rules are numbered from 1 in file order, dropped ones included; a `session` audit entry names its rule by that number.
- **Session rules** (§3.19) add `protocol` and `port` (an integer from 1 to 65535), and are used only by `sessionMaterialize`, never by `forward`; a rule without `protocol` is used only by `forward`:
  - `protocol = "http1"`: `header`, `methods` and `paths` as above; the position is the header. A `position` is a warning.
  - `protocol = "smtp"`, with `position = "auth-plain"` or `"auth-login"`, or `protocol = "pg"`, with `position = "password-cleartext"` or `"scram-sha-256"` (each allowed only where a rule names it): no `header`, `methods` or `paths` (a warning otherwise). Its `header` reads `''`.
  - **Trust anchors** (§3.19.6), on any session rule: `anchors` (base64 DER certificates, each starting with a SEQUENCE and at most 8 KB), `pins` (base64 SHA-256 of a public key, 32 bytes) and `roots` (`true` or `false`), at most 8 anchors and 8 pins. A rule with anchors or pins accepts only sessions the kernel verified against them, never the public roots, unless it says `roots = true`; a rule without them accepts the public roots, and `roots = false` there is a warning. The vault checks only their format: the kernel checks that an anchor is a CA (CA:true and keyCertSign) and the chain. Like every rule, they come only from the attested root-owned file, so only an approved `sudo` write sets them: no program, agent or page op can.
  - `port`, `position`, `anchors`, `pins` or `roots` without `protocol`, another `protocol`, or a missing or wrong `port`, `position`, `anchors`, `pins` or `roots` is a warning, and the rule is dropped.
- A record of kind `secret` is `active` when the file's `[secrets]` entry of its name holds the record's own placeholder and at least one rule names it. A placeholder from another vault or an old record doesn't activate anything.
- Nothing else in the file counts: no imports, profiles or other providers.

**`/etc/slicc/secrets-policy.toml`**, read by the vault only:

```toml
[exec]
NPM_TOKEN = true
GITHUB_TOKEN = { argv = [["/usr/bin/gh", "release", "upload"]] }
OPENAI_API_KEY = { shell = true }

[exits]
NPM_TOKEN = ["page", "device:7d1e4b0a9c2f5e83"]

[limits]
materialize_per_minute = 10
materialize_per_day = 200
shell_per_day = 5000

[reveal]
agent = false
```

- `[exec]`: `false` is an explicit off, `true` is `exec: 'any'`, exactly `{ argv = [[…]] }` is `'argv'` (each prefix an absolute program path), and exactly `{ shell = true }` is `'shell'`. Anything else, a table with other or extra keys included, is a warning, and `exec` stays `false`. VAULT-1d acts on them.
- `[exits]` is **optional**: a secret without a line may use every exit; a line restricts it to the exits listed (`page`, `proxy`, `tailscale`, `device:<id>`). `<id>` is the device's `DeviceId`, the stable id of its link certificate (a tray's 64 hex characters, or `local:…` for a CLI linked on the same computer), never its display name, which can be renamed or shared by two devices: one or more of `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` and `-`. An entry is compared exactly with the `exit` bios sends. Unknown names are dropped from the line with a warning, which leaves the line narrower, never wider.
- `[limits]` overrides the defaults above with positive integers.
- `[reveal]` has one key, `agent` (default `true`): `false` refuses every `ask` with `reveal` from the agent (Asks). Any other key, and an `agent` that isn't a boolean (which keeps `true`), is a warning. A change is audited as `{ kind: 'reveal', field: 'agent', from, to }`.

Accepted policy is kept per namespace in IndexedDB, and loaded when an embedder says hello. Each file is audited once per SHA-256 and verdict (the vault remembers the last 64 per file) as a `policy` entry, with `accepted`, any `warning`, and its `changes` against the previously accepted file: rules `added` or `removed`, `exec` modes, `exits` lines and `limits`. A pause and its end are always audited: the entry that starts one has `absent: true` and `sha256: null`. Any change to the accepted policy, or a new audit entry, pushes `changed` with `secrets`, `exits` and `audit`, and other vault documents of the namespace reload the policy. Each `policy` call reads, merges and writes the stored policy in one transaction, so two pages can't undo each other's update.

## Scrub state

`scrub { needed, version, ready }` tells bios and the agent whether output must pass the vault's scrubber before it reaches the model. It's per namespace:
- `needed` is false only when the namespace holds no plaintext at all: no record of any kind or state, removed ones included until they're purged.
- `version` counts every change to the namespace's set of values: each seal, rotation, removal, restore and purge.
- `ready` is false only when values exist, the vault is locked, and this frame has no compiled scrubber for the namespace: a reload with the lock on, before unlock. The scrubber (`@ai-ecoverse/slicc-scrub`, over every value of the namespace, records of every kind and state) is compiled whenever the frame holds the key and the set of values changed, and is kept in memory for the frame's life, so locking stops value use but never scrubbing.

It's in `status`, in `placeholders` replies and in every `placeholders` push. After `put`, `seal` and the kernel OAuth mutations, the push with the new pair goes out **before** the reply.

## Namespaces

Every record, request, audit entry and scrub version belongs to the origin that embeds the vault. The core frame takes it from the `event.origin` of the hello, and the button and the value frame from `location.ancestorOrigins[0]` (or the first message's origin when the browser hides ancestors). A branch preview of bios therefore gets its own empty vault and never sees seven's records. The popup shows the namespace of the button that opened it. The lock itself is one per vault.

## The embedding API (core frame)

The embedder (bios) loads `https://vault.sliccy.ai/` in an iframe and, after `load`, posts a hello carrying a port:

```js
iframe.contentWindow.postMessage({ type: 'slicc-vault', v: 1, op: 'hello', role: 'page', sudoGid }, 'https://vault.sliccy.ai', [port2]);
```

- The frame answers only when the message comes from its own parent window, from an allowed origin, matching `location.ancestorOrigins[0]` when the browser exposes it. Anything else gets no answer at all.
- On `port2` it answers `{ v: 1, op: 'welcome', role, status }`, or `{ v: 1, op: 'refused', error }` for another protocol version or an unknown role.
- Everything after that goes over the port. The namespace and the role are fixed by the hello. Requests are `{ v: 1, id, op, ...fields }`; replies are `{ v: 1, id, op, ...fields }` or `{ v: 1, id, error: { code, message, cause? } }`. Each port is answered in order (FIFO), except a `sealed` `ask` that waits for a human: the port goes on with the ops sent after it, and the ask is answered when it ends (`/dev/sealed`, the vault side).
- **Roles:** `page` (the default) is bios and spectrum. bios may hand spectrum a page port of its own, or relay; the messages are the same. `agent` is the port bios hands the agent worker: it may use only `redact`, `redactStream`, `push`, `idle`, `end`, `drop`, `endpoints`, `model`, `mcp`, `records`, `grant` and `refresh`, and anything else is `EACCES`. The agent port gets no events. Its ops are below (The agent's ops).
- **Values:** only `forward` (inside the head it returns, where an accepted rule allows it), `materializeConsume` (for an `[exec]` grant), `sessionMaterialize` (for a session rule, to the kernel's TLS writer, §3.19), `egress` (a refresh request) and a `sealed` `ask` with `reveal` (the reply to the program, after the user typed the value or allowed it in the value frame, in transit to the kernel only) put a value into the page. On the agent port only `model` and `mcp` do: their reply's prepared request carries the provider's or server's credential in its headers or URL, only for that provider's or server's own URLs, for the agent worker's transport to send at once. It must never be logged, stored, retried from storage or shown. No other op, event or reply carries a value, and no value ever reaches the model. The other way, a value comes from the page only with `put`, `seal` and a relayed `sealed` `oauthGrant`; `enter` lets the user type it in the value frame instead, so the page never holds it.

| op (page role) | fields | reply |
|---|---|---|

`put` and `seal` need the vault unlocked (`forgetLease` doesn't). They answer `EACCES` with a message starting `vault is locked` otherwise.

**Events** on page ports:
- `{ v: 1, event: 'status', status }` whenever requests, records, the scrub state or the lock change;
- `{ v: 1, event: 'placeholders', placeholders, scrub }` whenever either changes;
- `{ v: 1, event: 'changed', parts }`, with `parts` among `secrets`, `audit` and `exits`, so a view knows what to reload;
- `{ v: 1, event: 'refresh', name, source, expiresAt }`, when a J1 lease is due (below);
- `{ v: 1, event: 'egress', request }`, with a `MessagePort`, when the vault needs bios to send a request it built (below);
- `{ v: 1, event: 'cancelled', request, kind, state }`, with `state` `cancelled`, `withdrawn` or `expired`, when a request ends without an answer, to the page ports of every vault document of the namespace, before the `status` event that drops it from `waiting`. A request that leaves `waiting` without it was answered;
- `{ v: 1, event: 'asked', call, request }`, only on the port that sent the `sealed` `ask`, as soon as its request is stored and before any `status` event shows it: `call` is the `id` of that `sealed` op, so bios can withdraw it.

**Errors** use errno names: `EINVAL`, `ENOENT`, `EACCES`, `EEXIST`, `EAGAIN`, `ETIMEDOUT`, `ENOTCONN`, and `ENOTSUP` for ops this version doesn't have.

**`cause`** is the machine-readable reason for a refusal; match on it, never on `message`. `policy-paused` means the policy is paused (see Policy) and the vault may well be unlocked. `forward` (in `refused`), `materialize`, `materializeConsume`, `sessionMaterialize`, `sessionAnchors` (in `error`) and `test` (beside `verdict`) can return it, with `EACCES` or status `403` and `policy file missing: paused`. Every refusal of `forward` and `test` also has a `cause`, one per check, so a caller can tell the user what was refused without the `reason`, which names records and hosts: `no-placeholder`, `url-invalid`, `placeholder-in-url`, `placeholder-in-header-name`, `url-credentials`, `insecure-destination` (not https on port 443), `path-ambiguous`, `exit-encoded-bodies`, `exit-follows-redirects`, `record-removed`, `record-kind` (a secret sent where a model or MCP credential goes, or the reverse), `record-expired`, `vault-locked`, `no-rule`, `rule-domain`, `rule-request` (method, path or header), `rule-exit` (`secrets-policy.toml`), `placeholder-repeated`, `mcp-server` (the record isn't a credential of the MCP server at that URL), `value-overlaps`, `basic-invalid`, `basic-user`, `header-unsafe`, `users-off`, `endpoint-protected` (a secret sent to a model or MCP endpoint), `endpoint-model` (an MCP credential sent to a model endpoint), `mcp-body-framing` (`bodyPresent` missing or contradicted) and `changed` (the endpoints changed meanwhile). The other operations' refusals have no `cause`, a locked vault's included. `status.policy[]` says which file to restore: its entries `{ path, sha256, accepted, warnings, absent?: true, paused?: true }`, in page `status` replies and `status` events, name the missing file in `path`.

## `/dev/sealed`, the vault side

bios relays each kernel request unchanged as the `sealed` op, with the kernel's stamp. The vault validates and answers `{ v: 1, ...fields }` or `{ v: 1, error: { code, message, cause? } }`. A request over 64 KiB, one that isn't a single JSON object, one with `v` other than 1, and an unknown `op` are `EINVAL`, as is a missing or malformed stamp.

| op | fields | reply |
|---|---|---|
| `seal` | `name`, `value`, and for an MCP bridge `kind: "mcp"`, `server`, `url` | `{ placeholder, state }`. A new name creates a `process` record. An existing one is rotated and keeps its placeholder, but only when its value came from a process; a value from Settings, jerk, OAuth or an import is replaced only by uid 0, and anyone else gets `EEXIST`. **A bridge token** (§3.16.3, e.g. mcpcat's `--bearer`) is an `mcp` record bound to `server` and `url`, which must be a kernel-loopback URL (`http://<port>.kernel.localhost/…`, never 9222; anything else is `EACCES`). Any write that isn't a process's over a `process` record of another kind than `secret` (a page `put` or `seal`, a sign-in, an import) makes it an ordinary record, without the URL, under a new placeholder, so whoever sealed it keeps no placeholder of the new value; a `secret` keeps its placeholder, which every uid can read and the rules name. It records the sealing uid, and resealing it, even after it was removed, is allowed only for a `process` `mcp` record sealed by the same uid, or by uid 0; anything else, a user-entered record included, is `EEXIST` |
| `placeholder` | `name`, `server?` | `{ placeholder, state }` of the `secret` record, including `removed`; `ENOENT` when there's no record. For root, `server` changes the answer, and `name` is optional, below (Root and `mcp` records) |

- **Requests** expire 300 s after they're made. Each uid has at most one pending request per namespace that waits for a human (`value`, `ask`, `oauth`, `jerk-seal`, and `jerk` with `jop: "create"`); a second one is `EAGAIN`. `status` and `cancel` see only the caller's own requests (uid 0 sees all), and others get `ENOENT`. Only requests that wait for a human show in `status.waiting`.
- A value request is answered by the page's `put` with its `request` id. An `ask` is answered only in the value frame, never by a page op (`put`, `seal` and `answer` refuse it with `EINVAL`). A sign-in or lease (`oauth`, `jerk-seal`) is answered by `seal` with `request` (Tokens and refresh). Every other kind is answered by the page's `answer`. `cancel` ends any of them and pushes `{ v: 1, event: 'cancelled', request, kind, state: 'cancelled' }` to the page, which passes it on to J1 where it can.
- **J-8's jerk requests** (§3.7.1): the vault only keeps their state; bios learns of them from the relay and answers. `jop: "create"` and `unseal` are for root and cones only (J2): the kernel stamp must have `users: 'enforce'`, and either uid 0 or the `sudo` group among its `groups`. bios names that group's gid as `sudoGid` in its hello; a page hello without it clears the namespace's gid. A stamp without `groups`, a vault without `sudoGid`, or any other mode refuses: the request is `done` with `exit: 2` at once, before bios sees anything. The tag is kept for audit and display only.
- **Root and `mcp` records:** the placeholder of an `mcp` record a process didn't seal is for root only, since a process holding one can call that server through `forward` past a role's tool limits. Whoever seals a bridge token holds its placeholder. Root is a stamp with uid 0 and `users: 'enforce'`, not `mayManage`'s `sudo` group: a process a human approved (sudo, including standing approvals), or the judge the owner chose to delegate sudo to (slicc-agent's `sudo.approver = agent`, whose default is `user`, a person). That root can already do more than read a placeholder. A cone or scoop isn't root, and neither is any uid under another mode, where the stamp proves nothing. This is intentional: root is the owner, and sudoers decides who gets root, so root may use every Settings `mcp` record, by server, and `forward` of an `mcp` placeholder checks no uid or tag. The vault doesn't second-guess a sudo grant with a narrower per-program or per-server rule ([slicc-bios#1272](https://github.com/ai-ecoverse/slicc-bios/issues/1272)). Records match as kind `mcp`, source other than `process`, with `server` equal to the name given.
  - `placeholder` with `server`, for root: only a usable `mcp` record bound to that server answers, as in `list.mcp` (live, `ready` or `refreshing`, its name and server holding no value, so none while the vault is locked before its first unlock), with `{ placeholder, state, kind: 'mcp' }`. Given a `name`, it's the record of that name, else `ENOENT` "no record named NAME"; a `secret` of that name or a removed record never answers. Names in these refusals are scrubbed over every value. Without a `name`, it's the server's one record: `EINVAL` "several mcp records are bound to SERVER; ask for one by name" for more than one, and `ENOENT` for none. A record's name is never derived from its server's. Every other caller, and root without `server`, gets the `secret` answer, without `kind`.
  - `placeholder` with `name` and `server` answers for root when such a record, not removed, has that name and server. Anyone else, a wrong server, a removed record, a bridge token and a record with no `server` get the reply the op gives without `server`, the same as for no record. A `seal` under a taken name still answers `EEXIST`, as above.
  - `status` of a `done` `jerk` `status` request for `mcp:<server>` with no placeholder from a `secret` record: when both the request's stored stamp and the caller are root, and bios answered exit 0, and exactly one usable record (the rule of `list.mcp`) is bound to that server, the reply adds its `placeholder` and `record`. Several usable ones are `EINVAL` for root ("several mcp records are bound to SERVER; ask for one by name"), as for the agent's `refresh`; `placeholder` by name needs no such rule. When both are root and a record is usable but bios didn't answer exit 0, bios's reply stands. Every other reader, and any reader with no usable record, gets `{ state: 'done', exit: 3, message: "no token for mcp:<server> in seven's vault: run jerk mcp:<server> create" }`, whatever bios answered. The page and bios never see this rule: bios answers from `list.mcp`, before the caller is checked.
  - Neither reply carries a value, and neither read is audited, like every read of a placeholder; each use of one is, as `mcp` (Model and MCP endpoints). Where the value is filled is Which MCP credential goes where (§3.16.1): for a Settings record, an `https:` URL under the server URL the page registered; with no page server for that name, it's pinned on first use to the agent's URL for that server, until the page registers one; for a sign-in (`oauth:mcp`), any registered `https:` URL of that server.

**Asks.** `ask` is how a program (fnox, `sealed ask`) asks the user for a secret and waits for the answer in one call. The kernel adds the caller's stamp and `requester` (`{ exe, argv, cwd, tty, stdin }`, which a program can't set), bios adds `requester.kind` (`agent` for an agent connection's process, `user` for a terminal's), `name` (the stamp's user, or `uid <n>`) and `where` (the terminal's title or the agent's name), and relays it as the `sealed` op without a timeout.
- **The requester** must be `{ kind, name, where?, exe, argv, cwd, tty, stdin }`: `kind` `agent` or `user`; `name` and `where` strings, control characters stripped, cut to 128; `exe` and `cwd` absolute paths; `argv` a list of strings; `tty` a path or `null`; `stdin` `tty`, `none`, `pipe` or `file`. Anything else, and a `reveal` or `replace` that isn't a boolean, is `EINVAL`, as is a `kind` other than `agent` when the stamp's `tag` is `agent`. The caller is the op's `stamp`, as for every op.
- **At once:** with a live (not removed) `secret` of that name and neither `reveal` nor `replace`, the reply is `{ state: "done", placeholder, record }` at once, with no dialog and no request.
- **Mode:** otherwise it's a request of kind `ask`, in `mode` `reveal` when a live `secret` of that name exists, `reveal` is true and `replace` isn't, and `enter` otherwise. It shows in `status.waiting` as `{ id, kind: "ask", name, prompt?, mode, reveal, replace, requester, uid, tag, createdAt, expiresAt }`, counts toward the one request per uid (`EAGAIN`) and expires after 300 s. `prompt` is untrusted text.
- **`[reveal] agent = false`** in `/etc/slicc/secrets-policy.toml` refuses every ask with `reveal: true` from a `requester.kind` of `agent`, `enter` included, with `EACCES` before any request; while that file is paused, with `policy file missing: paused` and `cause: 'policy-paused'`. The default is `true`: the user is asked each time. It's checked again before a value goes out.
- **The answer** comes from the value frame (below): in `enter`, the value the user typed, sealed as a `secret` with source `settings` (a rotation that keeps the placeholder over an existing record, so `replace` sets a new value), audited as `seal` with `request`; in `reveal`, one click on **Allow**. The held reply is then `{ state: "done", placeholder, record }`, and with `reveal` also `value`: in `enter` the value just typed (`EAGAIN` if the record was sealed again meanwhile), in `reveal` the stored one. A reply with a value waits up to 10 s for the key while the vault is locked (`EACCES` `vault is locked` after that), and adds a `reveal` audit entry `{ name, uid, tag, exe, argv, cwd, requester, request }`, with `exe` and `cwd` scrubbed and `argv` joined with spaces, scrubbed and cut to 200 characters, as for `materialize`; `requester` is its `kind`. A record removed meanwhile is `ENOENT`.
- **The holder:** only the core frame that received an ask can reply to it. It holds a Web Lock for its life and stores its id in the request. When no live frame holds an ask's lock (its frame reloaded, closed or crashed), the ask is settled as `withdrawn` and `cancelled` is pushed with `state: 'withdrawn'`, at every page hello, before the welcome, and before any new `ask` or `request` is stored, so the uid isn't held up by it.
- **Otherwise** the held reply is `{ state: "cancelled" }` (the user denied, page `cancel`), `{ state: "withdrawn" }` (`cancel` with `reason: 'withdrawn'`: bios, when the program exited or closed the descriptor; nobody reads it) or `{ state: "expired" }` after 300 s, when the core frame that holds the ask also pushes `cancelled` with `state: 'expired'`.
- The reply isn't passed through any scrubber: the value goes to the kernel, which hands it to the program that asked. It never goes to the agent: every text the agent gets passes `redact`, and the value is always sealed in the vault.

## Tokens and refresh

The vault has no network stack, so sign-ins run in seven's page (route (b), §3.11) and the vault keeps only the results.
- **A sign-in's tokens:** bios runs the sign-in, does the code exchange, and hands the results to `seal`, keeping no copy:
  - the refresh token as `{ kind: 'grant', name, value, source: 'oauth:<provider>', oauth: { tokenUrl, clientId, scope?, resource? } }`. A grant is never injected and never exported; `tokenUrl` must be `https:`, without userinfo (`user:pw@`, `user@`, even an empty `:@`, also when hidden by whitespace or backslashes the URL parser normalises: any `@` in the authority refuses), and a `resource` must be an `https:` URL (or `http:` on 127.0.0.1, localhost or [::1]) without userinfo or fragment;
  - the access token as `{ name, value, source: 'oauth:<provider>', expiresAt, refresh: '<grant name>' }`. A grant name needs an `oauth:` source and `jerk-seal` a `jerk:` one (`EINVAL`), and a refresh uses the grant only when its source is the token's own (else the grant is missing).
  - With `request` (only for a `secret`; the id of a pending `oauth` request for the same provider as `oauth:<provider>`, or a `jerk-seal` request for the provider of `jerk:<provider>@…`) and `jerk` (`{ exit, user?, scopes?, expires_at? }`), `seal` also answers that request, in the same transaction that stores the record (a request that ended meanwhile refuses with `EINVAL`, and nothing is stored): its `/dev/sealed` `status` becomes `done`, with `jerk`, the record's `placeholder` and `record` state.
- **A J1 lease:** `{ name, value, source: 'jerk:<provider>@<device>', expiresAt, refresh: 'jerk-seal', lease? }`.
  - `lease` is `{ id, node }`: the host's lease id and the per-process `node` id of the link that created it (from that link's HELLO). Only a `secret` of a `jerk:` source takes one, both fields are 1–128 characters without control characters, no other field is allowed, and neither may hold a stored value or the value being sealed; anything else is `EINVAL`, whose message never carries them. It is metadata, kept with the record and never encrypted: a `seal` of the record (a lease refresh) replaces it, and one without `lease` clears it. No reply, event, audit entry or export bundle carries it: not `list`, `records`, `audit`, `status`, a `/dev/sealed` or agent op, nor an error.
  - `forgetLease { provider, lease, node }`, when the host revokes a lease (bios's `jerk-revoked` notice from the link whose HELLO named `node`): every `secret`, live or removed, whose source is `jerk:<provider>@…` and whose `lease` has exactly `id` equal to `lease` and `node` equal to `node` is purged at once, record and ciphertext, with no 30 days to restore it. The placeholders and the scrub version change, `changed` is pushed as for `remove`, each purge is audited as a `remove` entry of its name (`uid` and `tag` null, nothing of the lease), and it answers `{ forgotten: true }`. Anything else (another node, another id, a record without `lease`, another provider, an `oauth:`, `settings`, `process` or `import:` record, or one already gone) answers `{ forgotten: false }` and changes no record, the same for every reason. It needs no key, so it works while the vault is locked.
  - Every `forgetLease`, matched or not, also records the revocation, so a renewal still in flight is refused when it lands: the namespace's meta keeps the SHA-256 of `[provider, lease, node]` (never the strings) with the time, for 7 days, at most 256 of them (the oldest dropped; a repeat moves to the newest). A `seal` whose `lease` matches one, with the provider of its `jerk:<provider>@…` source, is `EACCES` "this lease was revoked", checked in the transaction that would store it, and stores nothing. A seal without `lease` or with another lease is unaffected. The list is never shown, exported or audited.
- **When a token is due** (5 minutes before `expiresAt`): the core frame checks once a minute, and right after a page says hello, for every connected namespace and for `secret`, `model` and `mcp` records alike, and `refresh { name }` asks for it at once. A page `refresh { name }` of a kernel-managed record is `EACCES` with message `managed OAuth records are not refreshed here` and does not call the IdP, decided on the read the refresh uses: a record that becomes managed meanwhile is not refreshed by it. That sweep still refreshes a due managed token. Vault frames of the same storage (several tabs) take a Web Lock per refresh source, so one grant is sent to its IdP by one frame at a time; a frame that finds the token changed while it waited (refreshed or sealed again) sends nothing and answers with the stored token's `{ state: 'refreshed', expiresAt? }`.
  - A `jerk-seal` token is announced once per `expiresAt` (kept in IndexedDB, so across frames), and again every 10 minutes while it stays unsealed, in case no live page heard it, with the `refresh` event, and bios runs J1 `seal` again (`{ state: 'requested' }`).
  - An OAuth token is refreshed in the vault with jerk-oauth: `refreshTokenRequestBytes` builds `POST <tokenUrl, serialized>` with `grant_type=refresh_token`, the refresh token, `client_id` and any `scope` and `resource` (form-encoded), from a byte buffer it zeroes, and the vault sends it through bios with the `egress` event. bios sends the request through its exits and posts `{ status, headers, body }` (or `{ error }`) on the event's port within 30 s. The event goes to the page port of the namespace that connected last. A port that doesn't answer in time (`ETIMEDOUT`), closed or not, keeps its ops and events but gets no more `egress`, and the next refresh goes to the page port before it. The vault checks the response with its own rules below and then with jerk-oauth's `parseRefreshResponse` (with the clock as whole seconds; a clock that isn't a safe integer is `EACCES: refresh failed: the vault's clock is invalid`), reads `access_token`, `expires_in` and any new `refresh_token`, checks them as values, and rotates the records in one transaction with the `refresh` audit entry (their placeholders stay; if the token or its grant was changed, removed or restored during the round trip, nothing is written and it answers `EAGAIN`). An `expires_in` of 0 makes the token due at once, and one that isn't a whole number from 0 to ten years is `EACCES: refresh failed: the IdP returned an invalid expires_in` (likewise a `refresh_token` that is present but not a string, a `token_type` that isn't `Bearer` in any case or is missing, and `access_token`, `refresh_token`, `token_type` or `expires_in` given twice: `EACCES: refresh failed: the IdP returned NAME twice`); a response carrying `error` fails even with a token; a response without `expires_in` leaves the new token without an expiry, so it isn't refreshed again until a new one is sealed. It answers `{ state: 'refreshed', expiresAt? }`, without `expiresAt` when the token has none. A failed refresh is `EACCES: refresh failed: <the IdP's error code>`, scrubbed; a code that isn't 1–128 characters of RFC 6749's error charset reads "the IdP sent an unreadable error", and `error_description` is never shown. Any other response jerk-oauth refuses is `EACCES: refresh failed: the IdP response is invalid`. MCP `grant` responses are parsed the same way. Without a connected page it's `ENOTCONN`.
- `egress` carries the refresh token to the page, in transit only; the response goes back to the vault, never to the kernel.

## Kernel OAuth refresh

`capabilities`, `oauthGrant`, `oauthStatus`, `oauthRefresh` and `oauthRemove` are `/dev/sealed` operations, not privileged page seals or agent operations. Bios relays them as `{ op: 'sealed', req, stamp, kernelOAuth: 1 }`, where `stamp` is the kernel's writer-based caller and `kernelOAuth` is a trusted **outer** assertion that bios implements the safe reply and scrub-completion contract. It is not authorization. A nested marker, stamp, source or kind cannot substitute. The request remains one JSON object of at most 64 KiB, with `v: 1`.

**Capability probe:** `{ v: 1, op: 'capabilities' }` returns `{ v: 1, capabilities: { kernelOAuth: 1 } }` only with that outer assertion; otherwise `{ v: 1, capabilities: {} }`. The other four operations refuse without it with `ENOTSUP`. Page `status.capabilities.kernelOAuth` describes vault support only. An old kernel or vault may reject the unknown probe with `EINVAL`; only while probing does that mean unsupported. Malformed replies and an offline vault never establish support. Eligible public-client sign-ins probe before exchanging tokens and never silently downgrade to access-only storage.

**Registration:**

```json
{
  "v": 1,
  "op": "oauthGrant",
  "name": "EXAMPLE_TOKEN",
  "provider": "example",
  "account": "default",
  "accessToken": "fake-access-token",
  "refreshToken": "fake-refresh-token",
  "tokenType": "Bearer",
  "expiresAt": 1800003600000,
  "oauth": {
    "tokenUrl": "https://auth.example.invalid/token",
    "clientId": "example-public-client",
    "authMethod": "none",
    "scope": "read",
    "resource": "https://api.example.invalid/"
  }
}
```

`name`, `provider`, `account`, `accessToken`, and `oauth.tokenUrl`, `oauth.clientId`, `oauth.authMethod` are required. `refreshToken`, `tokenType`, `expiresAt`, `oauth.scope` and `oauth.resource` are optional. The values obey the existing value rules. `tokenType` defaults to Bearer; comparison is ASCII case-insensitive without trimming. `expiresAt` is a nonnegative safe-integer **epoch millisecond** value, at most ten years ahead (315,360,000 seconds). Jerk converts its epoch seconds with checked multiplication. An absent expiry is unknown, not a promise of infinite validity. An absent refresh token creates a managed non-refreshable record and removes any previous owned grant atomically. An unknown expiry does not prevent forced refresh when a grant exists.

V1 supports only standard form-POST refresh with `authMethod: 'none'`. Confidential auth, supplied `clientSecret` or `client_secret`, reserved `auth`, captured `fields` and unsupported token types are `ENOTSUP`, never echoed. Other unknown fields at every request level are `EINVAL`. There are no caller-selected grant names, references, record kinds, ownership fields, headers or refresh templates. A client secret is never plaintext OAuth metadata: V1 creates no client-secret record and supports neither `client_secret_post`, Basic, assertions nor mTLS refresh.

`name` retains the environment-name syntax and 128-character maximum. `provider` is the exact non-MCP jerk ID, `^[a-z0-9][a-z0-9-]{0,127}$`; the existing model-provider validator is unchanged. `account` is the nonempty exact jerk account selector (user, workspace, otherwise `default`), at most 256 characters without C0/C1 controls. It is not an attested human identity. Public metadata may contain neither incoming tokens nor stored values. Access and refresh values cannot overlap in a protected form; refreshed values are checked against the stored binding too.

Registration creates a `secret` access record and, when supplied, a private `grant`, with source `oauth:kernel`, in one `sealAll` transaction. Private `kernelOAuth` metadata on both records reciprocally binds the owning access name, uid, provider, account, random identity and canonical OAuth configuration. The vault chooses a private grant name independently of public-name length. Source equality alone never permits reuse. All revisions, ownership, key generation, links, ciphertext and audit entries commit together or not at all. Ordinary authorized replacement of the access record retires its private grant in the same transaction; a generic seal cannot overwrite the private grant. Existing model/MCP binding and pasted-key restoration are unchanged.

Creation, status, forced refresh and removal require enforced users and the existing root-or-cone management check. A non-root manager may change only their own managed record; root may manage another uid's same identity. Non-root cannot replace a Settings/import/page-OAuth secret. An existing managed provider/account or immutable binding mismatch is `EEXIST`, even for root and on restorable tombstones: use another public name. Immutable fields are the canonical HTTPS token URL, client ID, auth method and resource. Token URLs reject userinfo, fragments, whitespace, backslashes and ambiguous paths; resource retains the existing HTTPS/loopback-HTTP rules without userinfo or fragments. Scope may change only with fresh credentials at registration. No model/MCP credentials or endpoint registrations can be created here.

**Status, forced refresh and removal:** each takes exactly `{ v: 1, op, name, provider, account }`, with `op` respectively `oauthStatus`, `oauthRefresh` or `oauthRemove`. Status and forced refresh use the same enforced-users and root-or-cone check as registration and removal. A caller who is not root, and whose uid is not the record's `kernelOAuth.uid`, receives `ENOENT` with message `OAuth record not found`, the same reply as a name that is not a managed record, and forced refresh performs no refresh. The owner and root keep every other reply, including `EEXIST` when the provider or account does not match. Status performs no network I/O and retains secret-placeholder visibility. Forced refresh accepts no replacement OAuth configuration. It uses the existing refresher and bios `egress`, with one attempt, shares a concurrently admitted successful refresh, and re-reads current status. It is `ENOTSUP` without a refresh source and `EACCES` with cause `oauth-reauth-required` for a dead/missing/invalid expected grant. Removal atomically soft-deletes access and owned grant, works while locked, and succeeds again for its tombstone. It preserves the existing 30-day retention and is not upstream provider revocation. Its only success is `{ v: 1, removed: true }`.

Registration/status/refresh success has exactly:

```json
{ "v": 1, "placeholder": "fnox_proxy_0123456789abcdef01234567", "state": "ready", "expiresAt": 1800003600000, "refreshable": true }
```

`expiresAt` is always epoch milliseconds or `null`. While locked, an expiry that cannot be checked with the current scrubber is withheld as `null`. `refreshable` describes a structurally live private grant, not network reachability. States are `ready` (unexpired or unknown expiry), `refreshing` (expired with a usable grant, not proof of active I/O), `expired` (expired without a grant), `reauth-required` (an expected grant is dead/missing/invalid), `removed`, and `locked` (no usability promise). No response includes a refresh placeholder, raw credential, OAuth configuration or provider response. The access placeholder stays stable through rotation and same-identity reauthentication.

Errors have exactly `{ v: 1, error: { code, message, cause? } }`. Codes are `EINVAL`, `ENOENT`, `EEXIST`, `EACCES`, `EAGAIN`, `ENOTSUP`, `ENOTCONN`, `ETIMEDOUT`, `EIO`; optional causes are `vault-locked`, `oauth-reauth-required`, `oauth-refresh-failed`. Messages are fixed, never provider or exception text. `ENOENT` means absent/non-managed for lookup; managed identity mismatch is `EEXIST`, not permission to fall back. Kernel and bios must validate actual `v: 1`, exact keys, placeholder grammar, state, safe integer/null expiry and boolean refreshability, and generate their own fixed errors. Unknown code/cause, incompatible version or unexpected response field is fixed `EIO`, never version-normalized success.

**Lifecycle and deadlines:** the four operations have a 40-second vault budget from receipt, including FIFO queue and commit, and at most five seconds waiting for the per-grant Web Lock. Kernel allows 45 seconds for them; the capability probe retains its ordinary 10-second kernel deadline. Bios egress remains 25 seconds and vault egress 30 seconds. A timed-out operation cannot commit later. Registration snapshots the record on admission and checks its revision in the writing transaction. Drop, reauthentication, lock or re-key invalidates an in-flight refresh's commit. `invalid_grant` atomically marks the private grant dead and immediately expires access, so ordinary forward/exec/session expiry checks refuse it; no further refresh is sent until reauthentication. Transient failure retains the grant. The stored endpoint is sent exactly with manual redirects, through a capable exit, never replayed after a transport failure.

Cancellation is not rollback: kernel close/withdrawal discards the local reply but does not propagate an abort to the vault. A commit can precede loss of its reply. Discard transient token buffers, never replay them or automatically delete a potentially newer credential; the next command reconciles current state with exact-identity `oauthStatus`. Keep local removal references until removal is confirmed. Vault publishes the new scrub pair before successful mutation replies. Bios must obtain the current `placeholders`/scrub pair and propagate it to workers before releasing success for `oauthGrant`, `oauthRefresh` or `oauthRemove`; failed propagation returns unavailable/timeout, never success.

**Discovery and migration:** existing device `placeholder` and `list` add `oauthManaged: true` only to managed access records, including the tombstones already visible through `placeholder`. This marker is not authority and carries no grant identity. It prevents an older transport from treating a managed record as an ordinary legacy secret. Jerk preserves nonempty env, then per-env-name vault lookup, then legacy status/CLI/config precedence. Confirmed managed records require authoritative readiness for both get and create's already-signed-in check; no stale-cache success or fallback around lock/offline/removal/dead/malformed state. Normal get refreshes within 300,000 ms; `--refresh` forces a refresh of the same managed record, never an unrelated one behind an env override. Local references hold only identity/name/placeholder. Old kernel sign-ins discarded refresh tokens and need one reauthentication; access tokens cannot recover them.

Existing implicit/access-only capture, multi-field capture and client-credentials reminting retain their non-refresh paths. Captured fields cannot be combined with managed refresh. Confidential interactive legacy sign-in remains access-only with an explicit warning before sign-in; confidential refresh stays unsupported. Kernel `refresh_env` cannot refresh directly outside the vault. Native jerk behavior remains unchanged. Deploy compatible vault/kernel/bios support before enabling the managed jerk path; dependency pins must reference published releases, not local fixture versions.

## Import and export

Spectrum's Settings › Secrets reads the file and the password, and bios hands them over. Both need the vault unlocked. Like every page op, `export` trusts the page: under rev 4 seven's page is trusted with values in transit (§8), and a compromised seven origin is out of scope.

**`export { passphrase }`** returns `{ bundle: Uint8Array, count }`, a backup of the namespace's records of kind `secret`, `model` and `mcp` that aren't removed. Grants aren't included, because they need a fresh sign-in. The passphrase needs at least 12 characters. The bundle is UTF-8 JSON:

```json
{ "format": "slicc-vault-bundle", "v": 1,
  "kdf": { "name": "PBKDF2", "hash": "SHA-256", "iterations": 600000, "salt": "<base64url>" },
  "cipher": { "name": "AES-GCM", "iv": "<base64url>" },
  "data": "<base64url>" }
```

`data` is AES-GCM 256 (additional data `slicc-vault-bundle`) over `{ "records": [{ name, kind, value, placeholder, source, createdAt, expiresAt? }] }`. A successful export sets `status.exportedAt`.

**`import { kind, bytes, password?, pick? }`** runs in two steps:
- Without `pick` it answers `{ stage: 'pick', candidates: [{ name, kind, exists, suggestedRules?, refused? }] }`, for the human to choose from. `refused` says why a candidate can't be imported.
- With `pick` it seals the candidates picked, each given as `{ name, kind }` or, for kind `secret`, as just its name, and answers `{ stage: 'done', imported: [{ name, placeholder, state }], skipped }`. `skipped` lists picked names that were refused or not in the file, and `reasons` maps each to a short reason ("not a valid name", "values shorter than 8 bytes can't be protected from the model", "it isn't in the file", …), never a value or part of one. `outcomes` lists every picked candidate as `{ name, kind?, imported, reason? }`, which tells two candidates of the same name and different kinds apart (`kind` is absent only for a picked name that isn't in the file). Each record is stored in its own transaction, which also reserves a bundle's placeholder, so a record either lands whole or not at all; one that can't be stored (its placeholder was taken meanwhile, the vault was re-keyed) is listed in `skipped`, and the rest still import.

| `kind` | `password` | what becomes a candidate |
|---|---|---|
| `bundle` | the export passphrase | each record, with its kind, source (`import:bundle` when it isn't a valid source), expiry, `provider`, `server` and `settings` (a `model` record without a provider is refused with "a model record needs its provider"), and **placeholder**, so the policy files still match. A placeholder used by another record of the namespace, or by another embedder of this vault, is refused ("this app already has this secret under another name", "another app that uses this vault already has this secret; use it there, or add it here by hand"), as is a name whose record here has another placeholder ("this app already has a different secret with this name") |
| `keepass` | the master password (KDBX 3 or 4, as kdbxweb reads them; Argon2 through hash-wasm) | each entry with a password, named after its title (upper-cased, other characters as `_`, a leading digit prefixed with `_`; a name already taken by an earlier entry gets `_2`, `_3`, …), source `import:keepass` |
| `six` | — | each `NAME=value` line of six's `secrets.env` (`export` and quotes allowed), source `import:six`. `NAME_DOMAINS` becomes `suggestedRules`: a `[[proxy.rules]]` stanza per exact domain, for the human to add with `sudo`, and a note for each wildcard, which isn't carried over |

Values are checked as at `put` (at least 8 bytes, no CR, LF or NUL, no placeholder). An existing name is rotated, keeping its placeholder. A candidate whose name and kind already belong to a kernel-managed record, live or restorable, is refused with "the record belongs to an OAuth sign-in", checked again in the transaction that would store it; that record and its grant stay. A wrong password or passphrase is `EACCES`.

## Exec

`fnox exec` (§3.5) asks for a one-shot ticket, and the kernel redeems it when it execs the child.

**`materialize`** (a `/dev/sealed` op) takes `names`, `path` (the absolute program fnox will exec), `argv` (exact, `argv[0]` included), `cwd`, and optionally `interpreter`: fnox's claim of the absolute shebang or binfmt interpreter of `path`, omitted for a native program. It's only a claim; the kernel's chain at consume decides. `shellGrants: true` (`fnox exec --shell-grants`) adds every `shell = true` secret to `names`, which may then be omitted. While the caller's stamp doesn't say `users: 'enforce'`, it's `EACCES` "kernel users must be enforce" in every `[exec]` mode, `shell` included (§3.16.2): with users off, every process is effectively root and the stamp proves nothing.
- Each name must be a `secret` record (`ENOENT` otherwise) that hasn't expired (`EACCES: NAME expired; refreshing`). `real` says which will get their value: removed records and secrets without an `[exec]` grant stay `false` and keep their placeholder.
- **`true`** (exec `any`): refused with `EACCES` when `path`, or `interpreter`, is a shell (`sh`, `bash`, `dash`, `zsh`, `fish`, `busybox`, `jsh`), an interpreter (`python*`, `node`, `deno`, `bun`, `perl`, `ruby`, `php`, `lua`, `wasmer`, `awk` and `gawk`/`mawk`/`nawk`, `sed`, `tclsh`, `expect`, `R`, `Rscript`, `irb`) or an env dumper or wrapper (`env`, `printenv`, `xargs`, `sudo`, `su`, `nohup`, `timeout`, `time`, `nice`, `strace`), by basename.
- **`{ argv = [[…]] }`**: `real` only when `[path, ...argv[1..]]` starts with one of the listed prefixes. A listed shell or interpreter is allowed.
- **`{ shell = true }`**: always `real`, with no program refusal.
- **Limits,** per secret and uid, counted from the audit log: `materialize_per_minute` (10) and `materialize_per_day` (200), and `shell_per_day` (5,000, with no per-minute limit) for shell grants. Over a limit is `EAGAIN: materialize limit for NAME (10/min)`.
- A locked vault answers `EACCES` (`vault is locked`).
- Each real name is audited as `materialize { name, exec, path, argv, argvSha256, cwd, pid, ppid, uid, tag, ticket, consumed: false }`. `argv` is joined with spaces, scrubbed, and cut to 200 characters; `argvSha256` is the SHA-256 of each argument followed by a NUL byte.
- The reply never carries a value. The ticket is 32 hex characters and expires after 30 s.

**`materializeConsume`** (a page op, from bios for the kernel at exec) takes `{ ticket, stamp, path, resolved, argv, cwd, interpreters, trusted }`, all from the kernel and relayed unchanged:
- `stamp` is the exec'ing process.
- `resolved` is the kernel-normalised file that actually runs: `path` with every symlink resolved.
- `interpreters` is the absolute, symlink-resolved shebang/binfmt chain the kernel resolved for `path`, empty for a native binary. A plain `#!/usr/bin/env X` (or `env -S`) is reported as the resolved `X`; `env` with any other option or a `NAME=value` assignment is reported as `env` itself.
- `trusted` is true when the program and every chain entry are root-owned regular files, not group- or other-writable, under root-owned, non-writable parents (the attestation rule). Under users `off` it's always false, and the consume is refused anyway.

The vault burns the ticket, then requires that:
- `stamp.users` is `enforce` (else "kernel users must be enforce"), it's unexpired and from this namespace, `stamp.ppid` is the pid that asked, and `path`, `argv` (element by element) and `cwd` are exactly the ones it was issued for;
- `resolved` is an absolute path (missing or malformed refuses), `interpreters` a list of absolute paths and `trusted` a boolean; a claimed `interpreter` from fnox equals `interpreters[0]` (without a claim, the kernel's chain is taken as it is);
- each real name is still granted by the policy as stored now (reloaded at materialize and at consume): a removed grant, or an `{ argv }` grant that no longer lists the command, refuses;
- under that name's mode, the chain passes:
  - `true`: no entry of `path`, `resolved` and `interpreters` is on the refusal list, so neither a `#!/usr/bin/env node` script nor a symlink `/tmp/l → /bin/bash` passes, and `trusted` is true ("the program or its interpreter can be changed by a non-root user" otherwise), so a renamed copy of a shell, which its non-root maker owns, doesn't pass either;
  - `{ argv }`: the listed program is `path`, and when `path` is a link to a refused program the rule must also list that `resolved` program by its real path ("list it in [exec] by its real path"), so a listed `/tmp/l` that is repointed to `/bin/bash` refuses. Whatever chain the kernel resolved for it is allowed, so a rule for `npm publish` allows `/usr/bin/npm`'s `node`. But when `resolved` or the chain is a refused program and `trusted` is false, it refuses ("the program or its interpreter can be changed by a non-root user"), and `env` and the other wrappers in the chain always refuse;
  - `{ shell = true }`: any program and chain, the explicit exception;
- no real record has expired meanwhile.

Any failure is `EACCES: ticket refused: …`, and the ticket stays burned, except for a policy that is paused or that changes before the values go out: the vault checks that in the transaction that marks the entries `consumed`, refuses with `policy file missing: paused` or `ticket refused: the policy changed meanwhile`, releases nothing, and keeps the ticket for its 30 s. It answers `{ values: { NAME: value }, placeholders: { NAME: placeholder } }` for the names that were real and still exist, and marks their audit entries `consumed`. The kernel swaps each env var whose value is exactly one of those placeholders, and compiles its own scrubber over these values for the child's output (S2).

## Forward

bios's exit router asks the vault to inject a request the kernel forwarded (an owner-bearing request that carries a placeholder), then sends it itself:

```js
const channel = new MessageChannel();
port.postMessage({ v: 1, id, op: 'forward', head, bodyPresent, owner, exit, rawTraits, streamCredit }, [channel.port2]);
```

- `head` is `{ method, url, headers: [name, value][] }`; `owner` the kernel's `{ pid, ppid, uid, gid, tag, users, groups?, user? }` (`users` must be `enforce`, else nothing is injected); `exit` the exit bios chose (`page`, `proxy`, `tailscale` or `device:<id>`, with the device's `DeviceId`); `rawTraits` that exit's `{ manualRedirects?, encodedBodies? }`; `bodyPresent` whether the request has a body, sent on every `forward`. `body` (bytes or a string) is read only for MCP requests (below); for every other request it stays in bios, because bodies are never injected.
- **The reply** says which `mode` the vault chose; bios never guesses it:
  - `{ mode: 'secret', head }`: the same head with the values filled in. It has no body, whatever bios sent.
  - `{ mode: 'mcp', head, bodyComplete: true, body? }`: the same, with `body` the complete request body scrubbed over every value (a JSON body stays valid JSON, as in `model` and `mcp`), the only bytes bios may send. A request with `bodyPresent: false` gets no `body` field; with `bodyPresent: true` it always does, an empty `Uint8Array` for an empty body.
  - `{ needsBody: true }`: an MCP request with `bodyPresent: true` and no `body`. Nothing else happened: no head, no `mcp` audit entry, no `usedAt`, no pin. Like any `forward`, it may run the one-time upgrade of legacy endpoints, with its `endpoints` audit entry. bios collects the complete body and calls `forward` again, with a new `MessageChannel`.
  - `{ refused: { status, reason, cause } }`: `403` with a one-line reason and its `cause` (see `cause`; `policy-paused` when the policy is paused), `400` for an MCP request whose `bodyPresent` isn't a boolean ("an MCP request must say whether it has a body") or is `false` with a `body`, or `502` for an exit with encoded bodies. A refused request must not be sent anywhere.
  - Malformed fields, and an MCP body above 32 MiB, are `EINVAL`.
- **The port:** on every reply but a `mode` one, the vault closes the transferred port.
- **The response** goes back over `channel.port1`, scrubbed: bios posts `{ op: 'response', status, statusText, url, redirected?, headers }`, then any number of `{ op: 'body', chunk: Uint8Array }`, then `{ op: 'end' }` or `{ op: 'error', message }`. The vault answers with the same messages, with `statusText`, `url`, every header name and value, the body and the error scrubbed over every value of the namespace. A value in its raw form comes back as its placeholder, anything else as `[redacted:NAME]`. The body is scrubbed as a stream; after 250 ms without input, a held tail shorter than 16 bytes is let through.
- **When the vault's values change** (a value sealed, rotated, removed or restored, in any vault document), the scrub of a response in flight is out of date, so the response is cancelled. In order for each message from bios and for the idle timer, the vault reads the scrub version and sends what follows from that message inside the same read transaction, so no write can commit between the check and the send. If it moved, nothing derived from that message goes out: any held tail is dropped, and the vault posts one `{ op: 'error', message: "the vault's values changed; send the request again" }` and closes the port. No credit follows. bios cancels the send.
- **Flow control** is opt-in: with `streamCredit: true`, and only then, the vault follows the scrubbed output of each `{ op: 'body', chunk: Uint8Array }` it gets with exactly one `{ op: 'credit', bytes }`, `bytes` being that chunk's `byteLength`, even when the output is empty because the scrub holds a tail back. Nothing else earns a credit: not the response head, an idle flush, `end`, `error`, or a chunk that isn't a `Uint8Array`.

**The injector**, fnox's proxy semantics:
- **Hosts** are compared lower-cased, without a trailing dot, in rules, the refusal list and MCP servers alike.
- **Refused before anything is sent:** an `owner` whose `users` isn't `enforce` ("kernel users must be enforce", §3.16.2; this covers kernel programs calling a registered MCP server, and the `/dev/sealed` `test` verdict, too); a placeholder in the URL or in a header name; credentials in the URL; a scheme other than `https:` or a port other than 443 (except §3.16.3's kernel servers, below); an ambiguous path (`.`/`..` segments, `\`, `%2e`, `%2f`, `%5c`, `%25`, checked on the raw URL); an exit with encoded bodies; no placeholder of this vault at all; a record that is removed, expired ("NAME expired; refreshing") or not a `secret`; a locked vault; no rule (in `/etc/fnox/config.toml`) whose exact domain, header, method and path allow it; a paused policy ("policy file missing: paused"); an exit the secret's `[exits]` line doesn't list; the same placeholder twice in one header value; any credential, `secret` or `mcp`, in any header, `authorization` included, on an exit whose raw `manualRedirects` isn't `true` ("NAME needs an exit that doesn't follow redirects"); a value that contains another stored value ("NAME's value contains another stored value"); CR, LF or NUL after substitution. The `/dev/sealed` `test` verdict goes through the same checks, on an exit it takes to be manual.
- **Paths** in rules are globs: `*` stays within a segment, `**` crosses segments, `?` is one character.
- **Injected:** each placeholder is replaced inside the rule's header value, so `Bearer …` and `token …` templates work. In `Authorization: Basic`, the credential is decoded, the user and password parts substituted (a substituted user may not contain `:`), and re-encoded. A Basic value that holds a placeholder but isn't valid base64 of UTF-8 is refused.
- **Audited:** each injection adds a `forward` audit entry `{ name, domain, method, path, rule, exit, uid, tag }`, all its text, the rule's included, scrubbed over every value before it's stored, and sets the record's `usedAt`. Never headers, bodies or values.

## Sessions

**`sessionMaterialize`** (§3.19, a page op that bios relays unchanged from the kernel) hands the kernel's TLS writer the secrets for one kernel-terminated TLS session (A2), for protocols `forward` can't carry: an http1 header on a kernel-made connection, SMTP AUTH, or pg's cleartext password or SCRAM-SHA-256. The kernel asks only after its own handshake verified the host (SNI, chain and hostname, whatever the caller's flags), never on a plaintext leg; it substitutes only at the position, uses each value once within 60 s, keeps it out of every process, fd, file, log and telemetry, and scrubs the session's read side (S2) for the values and their encodings. The vault picks the rules, so the kernel never parses `/etc/fnox/config.toml`.

```js
port.postMessage({ v: 1, id, op: 'sessionMaterialize', stamp, session, host, port: 587, protocol: 'smtp', position: 'auth-plain', verified: true, handshakeAt, exit, placeholders });
```

The fields are the kernel's session attestation:
- `stamp`: the kernel's stamp of the process that owns the socket; `users` must be `enforce` (else `EACCES` "kernel users must be enforce").
- `session`: the kernel's session id, 16 to 128 characters of `A-Z`, `a-z`, `0-9`, `_` and `-`.
- `host`: the name the kernel verified the leaf against, compared lower-cased without one trailing dot; `port`; `protocol` (`http1`, `smtp` or `pg`).
- `position`: `header:<name>` (lower-cased) for http1, else `auth-plain`, `auth-login`, `password-cleartext` or `scram-sha-256` (below).
- `verified`: the kernel's own verdict on the chain and the name; `handshakeAt`: when the handshake finished (epoch ms).
- `verifiedBy`: `roots` (the default; the kernel's bundled public roots) or `anchored` (a rule's anchors or pins, below), with `anchor`: base64 of the SHA-256 of the whole DER of the anchor that verified the chain, as `sessionAnchors` gave it, or the pin itself. `anchor` with `roots`, or a missing or malformed one with `anchored`, is `EINVAL`.
- `exit`: the exit the session leaves by (`page`, `proxy`, `tailscale` or `device:<id>`, with the device's `DeviceId`).
- `placeholders` (every position but `scram-sha-256`, which takes `scram` instead, below): 1 to 16 placeholders, every one found at the position, in one request. `head` (http1 only, required there): `{ method, path }`, the request line's method and target.
- A malformed field is `EINVAL`, and so is a `protocol` other than these or a `position` that isn't one of its protocol's; neither burns the session.

Once the fields check out, the vault burns the session in IndexedDB, in one transaction, so no vault frame of the namespace, now or after a reload, answers it again until 60 s after the later of the request and `handshakeAt`. Then it refuses the whole request with `EACCES` "session refused: …" when:
- the session already had a request, answered or refused: "this session already had its request";
- `verified` isn't true: "the kernel didn't verify the session's host";
- `handshakeAt` is in the future or more than 60 s ago: "the session is past its 60 s deadline";
- the vault is locked (`EACCES` "vault is locked: …"), at the start or by the point of release (below);
- for http1: an ambiguous path (as in Forward), or a URL under a model or MCP endpoint (Model and MCP endpoints).

Each placeholder then gets its value only when it is a `secret` record's, holding the placeholder `[secrets]` names, neither removed nor expired, with a session rule of that secret whose `protocol`, `domain`, `port` and position are the session's (and, for http1, whose `methods` and `paths` allow `head`), and whose `[exits]` line, if any, lists `exit`. A session can carry several secrets this way, each by its own rule. Just before answering, the records, the accepted policy and the registered endpoints are read again, at a fresh clock, in the transaction that audits the values. A value whose record was removed, expired or rotated meanwhile, or whose rule or `[exits]` line no longer allows it, is withheld. A session past its deadline by then, or an http1 URL now under a registered endpoint, refuses the whole request. That transaction is the point of release: if the vault locked before it, it writes nothing and refuses (`vault is locked`).

It answers `{ values: { [placeholder]: value } }` for those, and leaves the others out, so the kernel sends them as written. When none gets a value, it's `EACCES` with the first placeholder's reason: "NAME isn't a secret", "a placeholder of no record of this vault", "NAME's placeholder isn't the one /etc/fnox/config.toml names", "NAME was removed", "NAME expired", "no session rule in /etc/fnox/config.toml lets NAME be used", "no session rule lets NAME at PROTOCOL POSITION on HOST:PORT" (with " for METHOD PATH" for http1), "NAME isn't allowed on EXIT", or "the secret or its rule changed meanwhile". Each value handed out adds a `session` audit entry `{ name, session, domain, port, protocol, position, rule, verifiedBy, anchor?, exit, uid, tag }`, `rule` being the number of the rule that allowed it and `verifiedBy` and `anchor` how the kernel trusted the session (`anchor` only when `anchored`: the anchor's DER SHA-256 or the pin, never a value; entries written before 1.12.1 have neither, which means unknown, never `roots`), and sets the record's `usedAt`. It never includes the value. Stored values never hold CR, LF or NUL (Records), so a value can't break out of its position.

**`sessionAnchors`** (§3.19.6) is value-free: when the kernel's bundled roots fail a session only on trust (the leaf names the host and the chain is otherwise valid), it asks with `{ stamp, session, host, port, protocol, exit }` (checked as above; `users` must be `enforce`), and the vault answers `{ anchors, pins }`: every anchor and pin of the session rules for that `protocol`, `domain` and `port` whose secret's `[exits]` line, if any, lists `exit`, without duplicates, or empty lists. It burns nothing and needs no unlocked vault. The kernel then verifies the chain against those anchors only (never the program's `ca`), and asks `sessionMaterialize` with `verifiedBy: 'anchored'` and the `anchor` it used. A placeholder gets its value only by a rule that trusts the session: a rule with anchors or pins needs an `anchored` session whose `anchor` is one of that rule's own ("the anchor that verified the session isn't one of NAME's session rule" otherwise), or `roots = true` for a `roots` session ("NAME's session rule accepts only its anchors and pins, not public roots"); a rule without them takes a `roots` session only. So one rule's anchor never opens another rule's secret, and a pinned host can't fall back to a public CA.

**pg SCRAM-SHA-256** (`position: 'scram-sha-256'`, §3.19.5). The program's pg client computes its `ClientProof` from the password it holds, a placeholder, so the kernel can't see which one it used; the vault finds it from the proof. The request carries `scram: { clientFirstBare, serverFirst, clientFinalBare, proof }` and no `placeholders` (`EINVAL` otherwise, and `scram` at any other position is `EINVAL` too):
- `clientFirstBare` is `n=<user>,r=<client nonce>` and `serverFirst` is `r=<nonce>,s=<salt>,i=<iterations>`, with no extensions; the server's nonce must extend the client's, and `i` must be 1 to 100000.
- `clientFinalBare` is `c=<base64>,r=<the server's nonce>`, without anything after. `c=` decodes to exactly one of three things: the GS2 header `n,,` (`biws`); `y,,` (`eSws`, the program supports binding but saw no `-PLUS`); or `p=tls-server-end-point,,` followed by binding data of a SHA-256, -384 or -512 digest's length (32, 48 or 64 bytes), when the kernel offered the program `SCRAM-SHA-256-PLUS`. The binding data is opaque: it's used only as part of the program's AuthMessage, exactly as sent, to match the placeholder's proof, and it is never returned, logged or audited. Any other `p=` type (`tls-unique`, `tls-exporter`), an authzid, another length, or a malformed or non-canonical `c=` (it must re-encode to itself) is `EINVAL` before the burn.
- `proof` is base64 of the program's 32-byte `ClientProof`. Each message is at most 1024 characters. Anything else is `EINVAL`, before the burn.

The candidates are the placeholders that would pass the per-placeholder checks above for this session (a live `secret` with a `scram-sha-256` session rule for this host and port, whose `[exits]` allow `exit`), never other records; more than 16 is `EACCES` "more than 16 session rules' placeholders to try for SCRAM", before any hashing. For each, the vault computes RFC 5802's `ClientProof` with the placeholder as the password (PBKDF2-SHA-256 over the salt and iterations, then the Client Key, Stored Key and signature over `clientFirstBare,serverFirst,clientFinalBare`) and compares it in constant time. Only placeholders are hashed, never values, so it reveals nothing the program doesn't hold. Exactly one match is handed out as above (re-checked at release, audited with `position: 'scram-sha-256'`); none is `EACCES` "no session rule's placeholder matches the SCRAM proof", and more than one is `EACCES` "more than one placeholder matches the SCRAM proof". The kernel computes the real proof from the value, checks the server's real `v=` before giving the program one made from the placeholder, never passes on a server `e=` derived from the value, and wipes the value and every derived key.

## Model and MCP endpoints

The vault never injects a secret into a model or MCP endpoint, whatever a rule says.
- **The built-in list** is generated at build time (`scripts/endpoints.mjs`, into the gitignored `src/endpoints.json`) from every provider base URL in pi-ai's catalog (`@earendil-works/pi-ai`, pinned in `devDependencies`, the version slicc-agent runs), plus `bedrock-runtime.*` and `bedrock-runtime-fips.*.amazonaws.com`, Vertex AI's global `aiplatform.googleapis.com` (`google-vertex`), Azure OpenAI, AI services and Cognitive Services' OpenAI path (`*.openai.azure.com`, `*.services.ai.azure.com`, `*.cognitiveservices.azure.com/openai`, so Speech, Translator and the other Cognitive Services stay usable by rules), Adobe's LLM proxy (for the provider `adobe`), xAI's SuperGrok billing endpoint (`cli-chat-proxy.grok.com/v1/billing` for the provider `xai`, exactly that path and `GET` only, so slicc-agent can show the weekly allowance), and the model base URLs pi-ai has retired but that still serve models (`opencode.ai/zen`, `api.kimi.com/coding`): the refused set never shrinks when pi-ai drops a URL, though no key goes there. `*` is exactly one label (or segment). The published package's `piAi` field in `package.json` names the pi-ai version the vault was built against, so slicc-agent can check that both run the same catalog; Renovate bumps it with the pin, labelled `pi-ai-lockstep` and never automerged. Each entry is a host (with `*` for one label) and a path prefix (`*` for one segment, from templated segments); an entry may instead be an exact path (`exact`) and name the only methods a key is filled for (`methods`). `model` fills under such an entry only at exactly that path with one of those methods; the refused set still takes its path as a prefix, for every method.
- **Tenants (V3):** a built-in wildcard named after a tenant setting is bound to the key's own record. `gateway.ai.cloudflare.com/v1/{CLOUDFLARE_ACCOUNT_ID}/{CLOUDFLARE_GATEWAY_ID}/…`, `api.cloudflare.com/client/v4/accounts/{CLOUDFLARE_ACCOUNT_ID}/ai…` and the Azure hosts `{AZURE_OPENAI_RESOURCE_NAME}.openai.azure.com`, `.services.ai.azure.com` and `.cognitiveservices.azure.com/openai` fill a key only where each label or segment equals the record's `settings` entry of that name (Azure's host label case-insensitively, Cloudflare's path segments exactly), when the record has one. A record without them still reaches any tenant on that vendor's domain, as before; re-saving its `settings` binds it. Other wildcards (Bedrock's region, Vertex's location) aren't tenants and stay open.
- **Registered endpoints** only ever add, per namespace, and who registers them decides what they do:
  - **The page's `endpoints` op** (bios and spectrum, for what the user typed in Settings) adds model base URLs, a custom base URL for one model record as `{ name, url }` (an Azure APIM gateway or a Cloudflare gateway the owner typed for that account, say), and MCP servers. These are trusted: they join the refused set below. A `{ name, url }` is the only way a key reaches a URL outside the built-in list, and only that record's key: another record of the same provider never goes there. The vault stores the record's provider with it, and drops it when the record is removed.
  - **The agent's `endpoints` op** adds MCP servers, which only say where the agent's own `mcp` credentials may go (below). The vault never sets an agent-supplied `tokenUrl` for a server name a typed-in token is bound to. Once the page has registered a server name, every agent entry under that name is ignored, stored or new: the agent can't add to its `names`, set its `tokenUrl`, or register it at another URL. Its model base URLs and `{ provider, url }` entries are kept as URLs only: they never let a key go anywhere, and never refuse a secret rule. So a compromised agent worker can neither send a provider's key to a URL of its choosing nor make a user's secret rules inert by registering their host.
  - **Upgrade,** once per namespace, at the first hello the vault can scrub at, or before the first MCP credential is used after an unlock, (a namespace that registers anything for the first time after the upgrade has nothing to migrate):
    - the `{ provider, url }` entries earlier versions let an agent register are deleted, and never used meanwhile. Those a built-in base URL of that provider doesn't already cover (so not the Adobe proxy every agent registered) are listed as `purged: [{ provider, host }]`;
    - the agent-registered URLs of servers that typed-in `mcp` records are bound to (by `server`) are **adopted** into the page's servers, listed as `adopted: [{ server, host }]`, so existing setups keep working and the agent can't retarget them later. Typed-in tokens that are removed but restorable count too. Only the server's one concrete agent URL is adopted, bare (no `names`, no `tokenUrl`). A server name with no such URL (none, several, a `*` pattern, or one overlapping a page custom model URL) is held instead: none is adopted, and its tokens never pin on first use either, until the page registers the server. The decision uses only what was registered before the upgrade: agent registrations that arrive before the migration has run are kept aside and added only afterwards;
    - one `endpoints` audit entry holds both lists, scrubbed and with hosts only (never paths or queries, where a value could hide); none is written when both are empty.
- **The refused set** is the built-in list and the page's registrations, never the agent's.
- **At policy parse:** a rule that can reach only refused URLs (its domain matches, and the endpoint has no path prefix or every path of the rule lies under it), and an `smtp` or `pg` session rule whose domain matches any endpoint's host, is dropped and listed in `list.refused` with the reason `NAME: host is a model or MCP endpoint; the vault never injects there`. Other rules on the same host stay.
- **At request time:** `forward` refuses any URL under the refused set, before rules: `403 host is a model or MCP endpoint; the vault never injects there`.
- **Which MCP credential goes where (§3.16.1):** an `mcp` record is filled only on a server it belongs to, by where it came from:
  - **page-sealed** (Settings, `seal`, import): on an `https:` URL under the server URL the **page** registered for its server name (never at a `tokenUrl`). Until slicc-agent hands those URLs to the page, one without a page server is **pinned on first use** (§3.16.1, TOFU): on the agent's `mcp` path at its first fill, on a kernel `forward` at the first 2xx relayed through the vault. The pin is that agent server's URL (origin and path prefix; an agent server URL with a `*` pattern never pins, so the token isn't filled there), kept as the record's `url`, and audited as `endpoints { pinned: { name, server, host } }` (`name` is the record's); afterwards the agent's registrations for that server never count. A page registration for the server overrides the pin; once the page has dropped its registration for a server, the server is held, so its tokens never pin to an agent URL again until the page registers it. The page's `endpoints { unpin: [name] }` clears a pin (audited as `endpoints { unpinned: { name, server, host } }`), so the next use pins again;
  - **the agent's sign-ins** (`grant`, source `oauth:mcp`): on any registered `https:` URL of that server, since the agent already held the token;
  - **kernel bridge tokens** (§3.16.3, with their `url`): only on that URL;
  - **never** on a kernel loopback URL unless it is a bridge token, and never on a URL under a built-in or page-registered model endpoint.
- **Kernel programs calling a registered MCP server:** a `forward` that carries no `secret` placeholder and whose URL lies under a registered MCP server isn't refused but handled for that server only, a page server winning over an agent one on the same URL. Only `mcp` records bound to that server (by `server`, or listed in its `names`) and held as above are filled in; a `grant` or `model` placeholder is refused. A request that carries a `secret` placeholder is a secret request, whatever the agent registered: the refused set and the rules decide, so an agent's MCP registration can't make a user's rule inert, and a secret never goes over a kernel loopback `http:` URL ("credentials are sent only over https on port 443"). The reply is in `mode` `mcp`, and carries `body`, the complete request body scrubbed over every value, which bios sends instead of its own copy; the response is scrubbed as above; each call is audited as `mcp` with `server`, uid and tag.
- **`http://<port>.kernel.localhost/<path>`** (port 1–65535, never 9222, no explicit port) is the one `http:` form an MCP server may have (§3.16.3). Everything else must be `https:` on 443.

**Owner changes and requests in flight.** The vault re-reads the endpoints, the records and the scrub version as a last step before it hands a prepared head (agent `model`/`mcp`) or a forwarded one (kernel `forward`) back, so an owner change that has committed by then refuses it; a `forward` runs the injector again on what it re-read and writes its audit entry only if that gave the same head and nothing has changed since, in the audit's own transaction. A scrub version that moved at any point since the `forward` began refuses it too, so an MCP body is never scrubbed without a value held when it began. So a rule, exit, policy, record or endpoint change that has committed by then refuses it with `403 the endpoints changed meanwhile; send it again`, and leaves no audit entry and no `usedAt`. Otherwise, a request prepared before an owner change (the page removing, rotating, unpinning or re-registering something) may complete under the earlier state; the next request sees the change. This applies only to the owner's own changes: what the agent or a kernel program registers or sends never widens a binding, whatever the timing.

**Preparing model and MCP requests (§3.12).** Every model and MCP request of the agent worker goes through `model` or `mcp`, with or without a credential; the response comes back to the worker directly.
- **The head carries no value:** checked with the scrubber from before and after any refresh or rotation during the request, a raw value (in any form the scrubber knows) in the method, the URL, a header name or a header value is `EACCES` ("the request head carries a value; send its placeholder instead").
- **The body** (a string or bytes, at most 32 MiB of UTF-8) is scrubbed over every value of the namespace (S4), with both of those scrubbers, so neither a token refreshed for this request nor a value rotated meanwhile slips through and keeps its type; placeholders in it are left alone. A body that is JSON (a string, or bytes that are UTF-8, that `JSON.parse` reads) stays valid JSON, so a match can never cut one of its escapes: each string in it, names included, is scrubbed decoded and written back with `JSON.stringify` only when that changed it, and everything else is kept byte for byte. A match left across tokens or in a number then turns the smallest string, number or container holding it into a JSON string of its scrubbed text; if a form of a value were still left after that, the whole body is scrubbed as text. So is a JSON body nested more than 256 deep or of more than 200,000 strings, numbers and containers, and one whose walk would scan more than 4 times its length plus 1 MiB, so the scrub stays linear in the body. The URL must be `https:`, or for `mcp` the kernel loopback `http://<port>.kernel.localhost/…` (port 9222 refused) under that server's own loopback registration; anything else is `EACCES` ("model and MCP requests go out over https only").
- **The credential goes in by placeholder.** The worker sets a provider's API key (or `mcp.json`'s `${NAME}`) to the record's placeholder from `records`, and the vault replaces it with the value **only in the headers and the URL** (URL-encoded there), never in the body. Every placeholder of the namespace in the headers or URL must belong to the target, else `EACCES` ("NAME isn't a credential of TARGET; secrets are never sent to model or MCP endpoints"): for `model`, a `model` record of that `provider`; for `mcp`, an `mcp` record bound to that `server` or listed in its `names`; a bridge token sealed by a program only when the server's registration has exactly its `url` and the request is under that `url` itself (never at the server's `tokenUrl`). A `secret` or `grant` is never filled in, nor a credential whose value contains or equals another record's value in any form the scrubber knows except a 16-character fragment (`EACCES`). Every string in the replies of `model`/`mcp` (outside the prepared head), `records`, `grant` and `refresh`, and every error message, is scrubbed over every value, and a number whose digits are a value is left out.
- **Its own URLs only.** `model` fills a key only under that provider's built-in base URL (pi-ai's catalog, generated with the provider ids; at an exact or method-restricted entry only at that path with those methods) or a `{ name, url }` the page registered for that very record with `endpoints` (never the agent); `mcp` only under that server's registered URL (same scheme and port) or at exactly its `tokenUrl`, by the rules of Model and MCP endpoints (a page-sealed credential only where the page registered the server, a bridge token only at its loopback URL). Elsewhere a filled placeholder is `EACCES` ("NAME is sent only to TARGET's own endpoints"). A request without such a placeholder is only scrubbed, wherever it goes over `https:`, so OAuth discovery and client registration work.
- **`provider` is optional:** without it, the provider is the one of the single `model` placeholder in the headers and URL; with none or several, nothing is filled.
- **An expired record** with a refresh source is refreshed first, once per prepared request however often its placeholder appears, through `egress` (`EACCES` "NAME expired; refreshing" if that fails); one without is `EACCES` "NAME expired". A removed record is `EACCES`. A locked vault before its first unlock is `EACCES` ("unlock the vault to continue").
- **Consistency:** if the namespace's values change while a request is prepared by more than the one change each of its own refreshes makes, it's `EAGAIN` ("prepare the request again"), and a credential that a refresh rebinds to another provider or server is `EACCES`; `grant`'s kept fields also have the returned tokens replaced by their placeholders directly, and its record names and `expiresAt` are scrubbed against a value stored meanwhile.
- **The reply carries the value,** in `request.headers` or `request.url`, for the worker's transport to send at once. It is never logged, stored, retried from storage or shown; after a 401 the worker calls `refresh` once and prepares the request again.

**MCP OAuth (`grant`).** The worker registers the server with its `tokenUrl`, sends the code exchange through `mcp` (to exactly `tokenUrl`, with no credential), and hands the token endpoint's body to `grant`, holding it only in transit.
- `oauth.tokenUrl` must be `https:` and the server's registered `tokenUrl` (`EACCES` otherwise). A server or record name that holds a stored value or one of the returned tokens, in any encoded form, is `EINVAL`. The body is checked as for a refresh (an object with a string `access_token`, no `error`, `token_type` Bearer if present, a valid `expires_in`), and every token must be a valid value (`EINVAL` otherwise), before anything is stored.
- The access token is sealed as an `mcp` record bound to `server`, named `name` or `<SERVER>_ACCESS_TOKEN` (upper-cased, other characters as `_`, `MCP_` in front of a leading digit), with source `oauth:mcp` and `expiresAt` from `expires_in`. A `refresh_token` is sealed as a `grant` named `<name>_GRANT` with `oauth` and the same `server`, and becomes the token's refresh source. A live `<name>_GRANT` that isn't this token's own (a sign-in's, say) is `EEXIST`, checked in the writing transaction; a re-grant without a `refresh_token` removes the token's old grant unless another live credential shares it.
- Both records are written in one transaction, so `grant` stores all or nothing. The reply's `response` is JSON, a string or bytes like the input, with only `access_token` and `refresh_token` (as their placeholders), any string `token_type`, a numeric `expires_in` that isn't a stored value, and string `scope` scrubbed over every value; every other field, `id_token` included, is dropped. A `grant` whose access-token name is already bound to another server is `EEXIST`, checked in the same transaction.

**Model-provider sign-ins (`grant { provider }`, §3.12.1).** For the subscription sign-ins `xai`, `kimi-coding` and `openai-codex`, the worker runs the device-code flow and hands the vault the final token response: `grant { provider, name, response, settings? }`, with `name` the account's record name. The worker holds that response only in memory and never logs, stores, licks or transcribes it.
- **The token endpoint and client id come from the vault's own table** (`src/providers.ts`, taken from pi-ai's OAuth modules and checked against the installed pi-ai by a test): `https://auth.x.ai/oauth2/token`, `https://auth.kimi.com/api/oauth/token`, `https://auth.openai.com/oauth/token`. A `server` or `oauth` in the request is `EINVAL`, and any other provider is `ENOTSUP`.
- **The response** is checked like an MCP grant's, except that a missing `token_type` is taken as `Bearer` (none of these providers' clients reads it); one that's present and not `Bearer` is still refused.
- **The records:** the access token becomes a `model` record of `provider`, source `oauth:<provider>`, with its `expiresAt`; the refresh token, if any, a `grant` record `<name>_GRANT` that refreshes through `egress` as usual. Both are written in one transaction. The reply is `{ records: [{ kind, name, placeholder }], expiresAt? }`.
- **Its name and settings** (its own or, without any, those it inherits from the name's record, removed or not, checked in the writing transaction, which is `EAGAIN` if a value was sealed meanwhile) may hold neither a returned token nor a stored value (`EINVAL`), and `<name>_GRANT` must be free or this record's own grant, checked in the transaction that writes them (`EEXIST`); a removed grant still counts as another credential's while that removed credential can be restored. Over an earlier OAuth key whose grant has another name, that grant is removed unless shared. `response` is a string or bytes (any `ArrayBufferView`).
- **Under an existing name:** a record of another provider, even a removed one, is `EEXIST`. An earlier sign-in of the same provider is rotated, keeping its placeholder; if the new response has no `refresh_token`, the old grant is removed with it unless another live credential still refreshes from it. A key the user pasted (any source but `oauth:`), live or removed within the 30 days it can still be restored (one removed longer ago is gone, whatever its provider), is kept restorable: the sign-in replaces it (same placeholder), and `restore` of that name brings the pasted key back with its own source, settings, expiry and refresh link, and removes the sign-in's grant (unless shared). `list` marks such a record `replaced: true`. The stashed key stays encrypted under the vault key (re-sealed when the lock changes), is scrubbed like any value, and is what `export` writes for that name with the pasted key's own settings and expiry (a backup carries the pasted key, not the sign-in).
- **Remove** of the `model` record removes its grant too; `restore` restores both (for a record without a pasted key underneath).
- **Refresh failures:** the provider refusing the refresh is `EACCES "refresh failed: <code>"`; after `invalid_grant`, the grant is dead (not asked again), `records` shows the key `expired` and it isn't filled any more (`EACCES` "NAME expired; sign in again"), whatever its `expiresAt`, until a new sign-in. A network failure (`ENOTCONN`, `ETIMEDOUT`) keeps it `refreshing`.

**Bytes** are any `ArrayBufferView` (`Uint8Array`, `Int8Array`, `DataView`, a `Float32Array`, a Node `Buffer`), read as exactly its own bytes from `byteOffset` for `byteLength`, never the rest of its buffer. Anything else, a bare `ArrayBuffer` included, is `EINVAL` ("chunk must be bytes", or "texts must be a list of strings and bytes").

A stream is compiled against the namespace's values when it opens. If a value is added, rotated or removed while it's open, its next `push`, `idle` or `end` answers `EAGAIN` and the stream is gone: open it again and push the output from its start.

`redact` and `redactStream` need a compiled scrubber: with the lock on, before the first unlock since the frame loaded, they answer `EACCES` ("unlock the vault to continue"). They never return a value: matches are replaced, everything else passes through.

## The button (`button.html`)

A popup needs a click inside a vault document, so the way into the lock popup is this button. The embedder loads `https://vault.sliccy.ai/button.html` in an iframe and, after `load`, posts:

```js
frame.contentWindow.postMessage({ type: 'slicc-vault', v: 1, op: 'button', button: config }, 'https://vault.sliccy.ai');
```

**`config`** (`ButtonConfig` in the types):

| field | values | default |
|---|---|---|
| `intent` | `{ kind: 'unlock' }`, `{ kind: 'protect' }`, or `"auto"` | `"auto"` |
| `label` | text instead of the default label | per intent |
| `size` | `s`, `m`, `l` (24, 32 and 40 px high) | `m` |
| `variant` | `accent`, `primary`, `secondary` | `secondary` |
| `treatment` | `fill`, `outline` | `fill` |
| `quiet`, `disabled` | booleans | `false` |
| `scale` | `medium`, `large` | `medium` |
| `theme` | `light`, `dark` | the system's colour scheme |
| `dir`, `lang` | `ltr`/`rtl`, a language tag | `ltr`, `en` |

- **Sending `op: 'button'` again updates the same button in place.** The frame doesn't reload, and only the fields given apply on top of the defaults.
- `{ op: 'focus' }` moves keyboard focus into the button.
- `unlock` is labelled `Unlock vault`, and `protect` (set up or remove the lock) `Vault lock`. `"auto"` shows `Unlock vault` while the vault is locked, and otherwise no button at all (size 0×0).
- The background is transparent, and the button sits inside a 2 px inset so its focus ring isn't clipped. Pass `theme` to match the page: Chrome paints an iframe opaque when its colour scheme differs from the embedder's, so the frame takes the scheme of `theme`, and the browser default without it.

**Events** to the embedder, all `{ type: 'slicc-vault', v: 1, event, ... }`:
- `ready`, once;
- `size { width, height, inset }`, on every change, so the embedder sizes the iframe to it;
- `label { label }`, on every change, for the iframe's `title`;
- `focus { direction: 'next' | 'previous' }`, when Tab or Shift+Tab leaves the button;
- `popup { intent, state }`, with `state` `opened`, `done`, `cancelled`, `closed` (the window closed without an answer) or `blocked` (the browser blocked the window).

## The value frame (`value.html`)

The user answers an `ask`, or types the value of a page `enter`, inside this frame, so neither seven's page nor spectrum ever sees a typed value or can click Allow for the user. bios embeds it like the button (no sandbox, so Unlock can open the popup) and, after `load`, posts:

```js
frame.contentWindow.postMessage({ type: 'slicc-vault', v: 1, op: 'value', request, config: { theme, dir, lang, scale } }, 'https://vault.sliccy.ai');
```

- **The request** is read by its id in the frame's namespace (Namespaces). Sending `op: 'value'` again updates the same frame in place (`config` as for the button: `theme`, `dir`, `lang`, `scale`), and another `request` starts over. `{ op: 'focus' }` focuses its first control.
- **It shows,** per `mode` (a page `enter` request is always `enter`): `enter`, a masked field labelled `Value for NAME` (`Replace the value of NAME` with `replace`), checked as you type by the rules of Records (at least 8 bytes, no CR, LF or NUL, no placeholder), and **Save** (Enter in the field saves too); `reveal`, `EXE gets the plaintext of NAME` and **Allow**, a negative button. While the vault is locked it shows `Unlock the vault to continue.` and **Unlock**, which opens the popup (The popup) for `unlock`, and then the above.
- **Save and Allow stay disabled for 500 ms** each time they appear, so a click meant for something else can't land on them. Neither has an "always".
- **Save** seals the value as `/dev/sealed` Asks describe, or for a page `enter` as a record of its `kind` and binding with source `settings` (a rotation that keeps the placeholder over a live one), then empties the field and drops the value; **Allow** marks the request allowed, and is refused while the vault is locked. For an ask no core frame holds (Asks), both seal and allow nothing: the ask is withdrawn and the frame ends with `gone`. A seal answers an `ask`, `value` or `enter` request only when it is the record of the kind (`secret` but for `enter`) and name asked for, with source `settings` (`EINVAL` otherwise). Either then shows nothing more. A refused seal leaves the value in the field and says why.
- The background is transparent, the content sits inside a 2 px inset and takes the width it's given.

**Events** to the embedder, all `{ type: 'slicc-vault', v: 1, event, ... }`:
- `ready`, once;
- `size { width, height, inset }`, on every change;
- `focus { direction: 'next' | 'previous' }`, when Tab or Shift+Tab leaves the frame;
- `escape`, on Esc (not while composing): the embedder treats it as Deny;
- `done { request, state: 'sealed', name, placeholder, record }` (the sealed record's name, placeholder and state) or `done { request, state: 'allowed' }`, when the user answered here, after the vault documents were told of the change;
- `gone { request, state }`, when the request ended elsewhere (cancelled, withdrawn, expired or answered in another frame);
- `error { code, message }`: `ENOENT` for a request this namespace doesn't hold or that isn't an ask, or why a seal or Allow failed. Never a value.

## The popup (`popup.html`)

The button writes its intent to `intents` under a random 128-bit nonce and opens `/popup.html#<nonce>` in a 460×680 window. The popup claims that intent and shows the namespace it was opened for. Without a valid nonce it shows only "Nothing to do here". It asks the browser to make the vault's storage persistent.

| intent | what the popup does |
|---|---|
| `unlock` | unlocks with the passkey or passphrase, then closes |
| `protect` | while unlocked: **Protect with a passkey** (WebAuthn PRF), **Protect with a passphrase**, or, once protected, **Lock now** and **Remove protection** |

- A locked vault asks to be unlocked first, whatever the intent.
- A wrong passphrase or passkey says so ("That passphrase doesn't unlock this vault."), and a wrong passphrase is cleared from the field.
- A new passphrase needs at least 12 characters, typed twice. The popup says what's missing as you type, and **Protect** stays disabled until both fields pass.
- **Remove protection** asks first: "Remove protection? The vault will unlock by itself on this device." 

## Types for bios and spectrum

The npm package `@ai-ecoverse/slicc-vault` exports only TypeScript types, built from `src/contract.ts` (`exports` stays that one types entry; `dist/site` and `dist/headers.json` ship beside it as files): the port API (`Hello`, `Greeting`, `Request`, `Reply`, `VaultEvent`, `Role`, and `ResponsePart` and `ResponseAck` for a `forward` port), the button (`ButtonConfig`, `ButtonMessage`, `ButtonEvent`), the value frame (`ValueConfig`, `ValueMessage`, `ValueEvent`) and the page's `enter` (`EnterOptions`, `EnterResult`), asks (`AskRequest`, `AskReply`, `Requester`, `AskMode`, `SudoStdin`), the popup (`PopupIntent`, `PopupState`), the page's results (`SealResult`, `ImportResult`), and the data Settings shows (`SecretView`, `McpView`, `VaultStatus`, `ScrubState`, `PendingRequest`, `AuditEntry`, `ExitPolicyView`, `VaultList`). `Availability` (`connecting`, `waiting`, `locked`, `ready`) is for bios to tell spectrum "waiting for the vault" and "unlock the vault to continue". They mean:

- **`EpochMs`**: milliseconds since the epoch. **`DeviceId`**: the stable id of a linked device's link certificate, the same id bios uses for linked devices and trays, in `sourceDevice`, `device:<id>` exits (and `[exits]` lines) and `ExitPolicyView.devices[].device`; never a display name.
- **`Rule`**: `domain` is an exact lower-case host; `header` a lower-case header name; **empty `methods` or `paths` mean any**. A rule with `protocol` (`http1`, `smtp`, `pg`) is a session rule, with its `port` and, for smtp and pg, its `position`; show it as "PROTOCOL on host:port". `anchors`, `pins` and `roots` are its trust anchors (Policy).
- **`exec`**: `false` means the value is never revealed to a program; `any`, `argv` (with `execArgv`, the allowed argv prefixes) and `shell` are the `[exec]` modes under which `fnox exec` may hand it to a program.
- **`exits`** is present only when `/etc/slicc/secrets-policy.toml` restricts that secret; absent means every exit (`page`, `proxy`, `tailscale`, `device:<id>`).
- **`url` and `pinned` in `list`** (`mcp` records): the URL a credential is bound to, the full URL scrubbed over every value, and `pinned: true` when that binding is a first-use pin (§3.16.1) rather than a kernel bridge's. A page registration for the server overrides a pin, so compare it with the page's own registrations.
- **Bindings in `list`:** read under one scrub version (retried, then `EAGAIN`), `provider`, `server` and `settings` are scrubbed over every value (a setting whose name holds one is dropped), and left out while the vault is locked before its first unlock.
- **`kind`**: `secret` (a credential programs use through rules), **`grant`** (a sign-in's refresh token, never injected; show it as "Sign-in"), `model` (a model provider key), `mcp` (an MCP server credential). `provider` and `account` name the service and the signed-in account where one is known; a `model` record always has its `provider`, an `mcp` record may have its `server`, and either may carry non-secret `settings`.
- **Who did it:** `uid` and `tag` are the kernel stamp for entries a program or the agent caused (`/dev/sealed` seals, `forward`, `mcp`, `materialize`, `session`). Every entry from a page-role op (`put`, `seal`, `remove`, `restore`, `import`, `policy`) and from the vault itself (`refresh`, `endpoints`) has `uid: null, tag: null`, older entries included. Spectrum shows page ops as "by you", `refresh` and `endpoints` as "automatically", and `policy` entries with no "by …".
- **`AuditEntry`**: `endpoints` is vault-originated: the upgrade's `purged` (show it as "Removed custom model URLs an agent set") and `adopted` ("Kept the MCP servers your tokens use"), a `pinned` MCP token ("pinned to <host>", with an Unpin action) and an `unpinned` one; `forward` is a use of a value in a request, with the exit that carried it; `mcp` a kernel program's call to a registered MCP server; `session` a value handed to the kernel for a verified TLS session (show it as "Sent over PROTOCOL to host", with "trusted by public roots" or "trusted by its pinned anchor" from `verifiedBy`, and nothing when an older entry has no `verifiedBy`); **`materialize` is shown as "Revealed to a program"**; `reveal` (`AskRevealEntry`) is an `ask` whose value went to the program `exe`, with the `requester` kind; a `seal` with `request` answered that request; `seal`, `remove`, `restore` and `policy` (with its `changes`) record changes. Every entry has a `seq` for paging.
- **`SessionTarget`**: a `sessionMaterialize` request's protocol, position and what goes with it: `placeholders` (and `head` for http1) for every position but `scram-sha-256`, which takes `scram` (a `ScramExchange`) and no `placeholders`.
- **`VaultList.mcp`** lists usable `mcp` records for bios's jerk `status`, without a placeholder or source (`list`); treat every entry as usable, whatever its `state`.
- **`ErrorCause`**: the machine-readable `cause` on `VaultError`, on `ForwardResult`'s `refused` and on `TestVerdict` (the `/dev/sealed` `test` reply): `policy-paused`, and on `forward` and `test` one per check (see `cause`).
- **`VaultList.refused`** lists rules the vault dropped because they name a model or MCP endpoint.
- **`PendingRequest.prompt`** is untrusted, agent-written text of at most 200 characters.
- **`PendingRequest` of kind `ask`** also has `mode`, `reveal`, `replace` and `requester`. `requester` came from the kernel and bios, so it can be shown as trusted, unlike `prompt`.
- **`ExitPolicyView`** is read-only: the secrets `/etc/slicc/secrets-policy.toml` restricts to certain exits.

## Develop

```sh
npm install
npm run build      # dist/site, dist/headers.json and dist/types
npm run lint
npm test           # Chromium integration tests
npm start          # vault on http://vault.sliccy.localhost:8790, a test embedder on seven.sliccy.localhost
```

- **Integration tests** (`test/integration/`) run the built vault on a local server that sends the production headers, at `http://vault.sliccy.localhost:<port>`, with test embedders on `seven.`, `preview.` and `evil.sliccy.localhost`. Chromium treats `*.sliccy.localhost` as one site and as a secure context, so the embedded frame gets the same first-party storage it gets under `sliccy.ai`. They use slicc-shared-web's CDP harness, plus a second CDP session for popups and the virtual WebAuthn authenticator. They collect no browser coverage (nothing reads it, and with `coverage: []` the harness attaches nothing); `SLICC_COVERAGE=1 npm test` turns it on locally. The unit tests' diff-coverage gate is separate. `kernel.test.mjs` runs exec tickets end to end against the real kernel (`@ai-ecoverse/slicc-kernel/node` with wasm-bash and wasm-coreutils, test dependencies only): its `/dev/sealed` hook relays to the built vault, so a `materialize`, the spawn with `SLICC_SEALED_TICKET`, the kernel's `materializeConsume`, the value swap and S2's scrubbing of the child's output all run as in seven, and with users `off` nothing is revealed.
- **Unit tests** stay in the gitignored `test/unit/` (`npm run test:unit`), and the pre-commit hook requires them to cover every changed line of `src/`.
- The Biome, TypeScript, lefthook and Renovate configuration comes from [slicc-shared-web](https://github.com/ai-ecoverse/slicc-shared-web). There are no comments in any file.

## Release and deploy

- **Releases:** semantic-release on `main` (the pipeline's release job) tags a version from the conventional commits and publishes the package to npm with trusted publishing, which names `ci.yml` (`fledgling.workflow`; `npm run trust` registers it). The published files are `dist/types`, `dist/site` and `dist/headers.json`. `exports` stays the types entry.
- **Deploy:** when semantic-release tags a new version, the pipeline's `after-release` command (in `ci.yml`) builds with that version and publishes `dist/site/` to `vault.sliccy.ai` from the `production` environment; a push to `main` that releases nothing deploys nothing. The packages of ours that the site bundles (`@ai-ecoverse/slicc-scrub` and `@ai-ecoverse/jerk-oauth`) are `dependencies`, which Renovate's `config:recommended` commits as `fix(deps)`, so each bump releases and deploys; every other bump is `chore(deps)` and waits for the next release. `dependencies.test.mjs` keeps the `dependencies` to exactly the packages of ours that `src/` imports. Every pull request publishes its branch to `vault-<label>.sliccy.ai` through the pipeline's `deploy` input (in `ci.yml`), in the `staging` environment: it builds with `VAULT_VERSION=0.0.0-$GITHUB_SHA` and writes the published URL to `$GITHUB_OUTPUT` as `url`, so the tests and reviewers get it as `STAGING_URL`. The publish route takes the label from the pull request token's `head_ref`, the branch. A branch without a pull request publishes nothing. The preview needs no secret, so `deploy-secrets` is unset, which since slicc-shared-web v2.11.2 hands the `deploy` command no secret at all. Both use GitHub's OIDC token against sliccy-ai's `/api/publish` route (`edge/publish.mjs`), with no stored secret. `edge/publish.mjs` ends with the verdict line `publish: PASS <url> <sha>`, and both publishes fail without it, so a script that exits without publishing can't read as a pass. It runs as the main module also through a symlinked checkout or workspace: both sides of that check are real paths. A `manifest` answer without an `https://` URL fails the publish.
